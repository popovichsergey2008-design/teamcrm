# Этап 2 — Real-Time Unit-Economics

Этап 2 превращает систему из обычного трекера задач в инструмент финансового контроля. Это ядро продукта: каждая задача получает денежную себестоимость, пересчитываемую в реальном времени, а руководитель видит маржинальность проектов в моменте, а не в конце месяца.

Закрывает киллер-фичи master-спеки: **№1 Real-Time Unit-Economics** и **№5 Сквозная маржа Deal → Project (Deal-to-Delivery P&L)**.

Миссия: фиксировать факт работы интерактивным тайм-трекером, фоновым движком пересчитывать себестоимость задач по версионным ставкам, агрегировать P&L проектов и поднимать алерты при падении маржи — всё с realtime-доставкой и строгой изоляцией финансов от роли `client`.

Non-goals этапа (выносится в Этапы 3–5):

- никакого ИИ, голосовых дейликов, авто-тайм-трекинга из Telegram (Этап 3 — он будет *поставщиком* событий трекинга, но сам трекер и движок принадлежат Этапу 2);
- никакого расчёта Velocity и предиктивных сроков (Этап 4);
- никакого клиентского портала как отдельного продукта (Этап 5) — но контракт изоляции финансов от `client` обязателен уже здесь;
- никакого вычисления эмбеддингов и RAG (Этап 5).

## Шаг 2.1. Интерактивный тайм-трекер

Кнопка «В работу / Пауза» в каждой карточке задачи. Бэкенд фиксирует точные таймстампы (`timestamp_start`, `timestamp_end`) в `time_logs`. Ручной ввод времени («я работал 3 часа») искажает реальность — нужна фиксация факта работы.

### Контракт трекера

- **Один активный таймер на пользователя.** В любой момент у пользователя может быть не более одной открытой записи (`timestamp_end IS NULL`). Старт нового таймера атомарно закрывает предыдущий открытый (если есть) и открывает новый.
- Инвариант обеспечивается на уровне БД частичным уникальным индексом, а не только проверкой в коде:

```sql
CREATE UNIQUE INDEX uq_open_timer_per_user
    ON time_logs (tenant_id, user_id)
    WHERE timestamp_end IS NULL;
```

- старт: `INSERT` с `timestamp_start = now()`, `timestamp_end = NULL`; закрытие предыдущего и старт нового — в одной транзакции;
- стоп/пауза: `UPDATE ... SET timestamp_end = now()` для открытой записи;
- запрещены записи с `timestamp_end < timestamp_start` и нулевой длительностью (валидация);
- закрытие записи (`timestamp_end` проставлен) ставит задачу в очередь пересчёта себестоимости (`economics`);
- трекинг возможен только по задачам доступного пользователю проекта (tenant + проектный доступ).

Доменные события: `time.started`, `time.stopped`. Они **не** содержат денежных полей и могут идти в обычные проектные комнаты; событие изменения стоимости (`task.cost_changed`) — отдельное и финансовое (см. ниже).

**DoD шага:** кнопка старт/стоп фиксирует точные таймстампы; невозможно иметь два открытых таймера у одного пользователя; закрытие записи триггерит пересчёт.

## Шаг 2.2. Движок динамического расчёта себестоимости

Фоновый процесс (очередь `economics` в RabbitMQ) пересчитывает текущую стоимость задачи. Формула (ТЗ, Шаг 2.2):

```
Текущая_стоимость_задачи = Σ ( затреканные_секунды / 3600 × почасовая_ставка_исполнителя )
```

### Контракт расчёта

- **Версионная ставка.** Стоимость считается по ставке, действовавшей на момент интервала трекинга (`rates.effective_from/effective_to`), а не по текущей. Если `time_log` пересекает границу смены ставки, интервал **разбивается** на сегменты по границам версий ставки, и каждый сегмент умножается на свою ставку. Это нетривиальный, но обязательный контракт: без него историческая себестоимость «плывёт» при изменении ставки.
- **Себестоимость — производная, пересчитываемая целиком.** Воркер не инкрементирует `cost_current`, а **пересчитывает её полностью** из всех `time_logs` задачи. Это делает пересчёт идемпотентным: повторная обработка того же сообщения даёт тот же результат, без задвоения.
- **Триггеры пересчёта:**
  - событие закрытия `time_log` → постановка задачи в очередь;
  - расписание — догоняющий пересчёт открытых таймеров примерно раз в минуту (ТЗ: «каждую минуту пересчитывает»), чтобы стоимость текущей работы росла визуально в реальном времени;
  - изменение ставки `rates` → пересчёт всех задач, затронутых сменой.
- **Коалесинг.** Частые обновления одной задачи схлопываются: на задачу/bucket планируется одна due-обработка, а не очередь дублей.
- **Транзакционная запись.** Воркер в одной транзакции пишет `tasks.cost_current`, обновляет агрегаты P&L проекта (см. Шаг 2.3) и инвалидирует/обновляет кэш Redis. Затем эмитит `task.cost_changed` и (при изменении) `project.pnl_changed`.
- **Стоимость текущей (открытой) работы** считается до `now()` для незакрытого `time_log`; это даёт «растущую» себестоимость на доске.

Псевдоконтракт сегментации интервала по ставкам:

```
для каждого time_log задачи:
    интервал = [timestamp_start, timestamp_end или now()]
    для каждого сегмента интервала, попадающего в окно одной версии ставки:
        стоимость += (секунды_сегмента / 3600) × ставка_этой_версии
```

**DoD шага:** себестоимость задачи равна сумме по версионным ставкам; пересчёт идемпотентен; стоимость текущей работы растёт в реальном времени; смена ставки корректно пересчитывает историю.

## Шаг 2.3. Дашборды маржинальности (P&L в моменте)

Аналитические панели по каждому проекту. Из бюджета вычитается динамическая себестоимость всех задач. Цель — предотвращение кассовых разрывов: если маржа падает ниже порога, система бьёт тревогу **до** того, как проект уйдёт в минус.

### Контракт P&L

- **P&L проекта в моменте:**

```
себестоимость_проекта_факт = Σ cost_current задач проекта
маржа_факт_%               = (бюджет − себестоимость_проекта_факт) / бюджет × 100
```

- агрегаты хранятся денормализованными полями проекта (`cost_actual`, `margin_actual`) и обновляются движком в той же транзакции, что и `task.cost_current`;
- дашбордные представления кэшируются в Redis с TTL и инвалидируются при пересчёте; любое значение восстановимо из PostgreSQL;
- **Сквозная маржа Deal → Project (фича №5):** для проекта, развёрнутого из сделки (`projects.deal_id`), плановая маржа (`deals.planned_margin`) сверяется с фактической (`projects.margin_actual`) в реальном времени. Дашборд показывает обе и расхождение — собственник ловит убыточные сделки до закрытия проекта.

### Контракт алертов

- порог маржи настраивается на уровне проекта (`projects.margin_alert_threshold`, по умолчанию из настройки tenant, например 20%);
- при пересчёте, если `margin_actual` опускается ниже порога, движок поднимает `alert` (idempotent по `(project_id, тип, активный период)` — не плодит дубли, пока маржа ниже порога);
- алерт уходит проджект-менеджеру/владельцу через очередь `notifications`; событие `alert.raised`;
- при возврате маржи выше порога активный алерт закрывается.

**DoD шага:** дашборд P&L показывает факт vs план в реальном времени; алерт поднимается при пересечении порога вниз и закрывается при возврате; алерты не дублируются.

## DDL (добавления к Этапу 1)

Схема Этапа 1 уже содержит `time_logs`, версионные `rates`, `tasks.cost_current`, `projects.budget`, `deals.planned_margin`. Этап 2 добавляет агрегаты P&L, порог и сущность алертов.

```sql
-- Один активный таймер на пользователя (см. Шаг 2.1).
CREATE UNIQUE INDEX uq_open_timer_per_user
    ON time_logs (tenant_id, user_id)
    WHERE timestamp_end IS NULL;

-- Денормализованные агрегаты P&L проекта (пишет только движок economics).
ALTER TABLE projects
    ADD COLUMN cost_actual           NUMERIC(14,2) NOT NULL DEFAULT 0,
    ADD COLUMN margin_actual         NUMERIC(6,2)  NULL,           -- %, NULL если бюджет не задан
    ADD COLUMN margin_alert_threshold NUMERIC(5,2) NULL,           -- порог, NULL = брать из tenant
    ADD COLUMN economics_recomputed_at TIMESTAMPTZ NULL;

-- Настройка порога по умолчанию на уровне арендатора.
ALTER TABLE tenants
    ADD COLUMN default_margin_threshold NUMERIC(5,2) NOT NULL DEFAULT 20.00;

-- Алерты (каналы проактивного контроля; на Этапе 4 расширяются риском срыва).
CREATE TABLE alerts (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id   BIGINT NOT NULL REFERENCES tenants(id),
    project_id  BIGINT NULL REFERENCES projects(id),
    task_id     BIGINT NULL REFERENCES tasks(id),
    type        VARCHAR(48) NOT NULL,           -- margin_below_threshold | ...
    severity    VARCHAR(16) NOT NULL DEFAULT 'warning',
    payload     JSONB NOT NULL,                 -- {budget, cost, margin, threshold}
    raised_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    resolved_at TIMESTAMPTZ NULL                -- NULL = активен
);
-- Не более одного активного алерта данного типа на проект (idempotent raise).
CREATE UNIQUE INDEX uq_active_alert_per_project_type
    ON alerts (tenant_id, project_id, type)
    WHERE resolved_at IS NULL;
CREATE INDEX idx_alerts_active ON alerts (tenant_id, resolved_at);
```

Контракты схемы:

- денормализованные P&L-поля проекта пишет **только** движок economics, в транзакции пересчёта;
- частичный уникальный индекс `uq_active_alert_per_project_type` делает idempotent-raise алертов гарантией БД, а не только кода;
- все новые поля и таблица scoped по `tenant_id`.

## Контракт очереди `economics`

| Поле сообщения | Назначение |
|---|---|
| `kind` | `recompute_task` \| `recompute_project` \| `recompute_on_rate_change` |
| `tenant_id` | scope |
| `task_id` / `project_id` | цель пересчёта (nullable по виду) |
| `reason` | `time_log_closed` \| `scheduled_tick` \| `rate_changed` |
| `dedup_key` | ключ коалесинга на задачу/bucket |

Правила: воркер идемпотентен; сообщение не является source of truth (источник — `time_logs` + `rates`); при падении воркера сообщение переобрабатывается без двойного применения (полный пересчёт). Догоняющий тик планируется по расписанию (Этап 0 уже даёт RabbitMQ; планировщик — внутри `economics`-воркера или отдельный cron-producer).

## Realtime-события Этапа 2

Финансовые события **не публикуются в клиентские комнаты** (фича №9; роль `client` физически не получает себестоимость/маржу — это проверяется тестами):

| Событие | Финансовое? | Аудитория |
|---|---|---|
| `time.started` / `time.stopped` | нет | участники проекта |
| `task.cost_changed` | **да** | только internal-роли проекта |
| `project.pnl_changed` | **да** | только internal-роли проекта |
| `alert.raised` / `alert.resolved` | **да** | только internal-роли (PM/owner) |

## API-контракт Этапа 2 (добавления)

Все ответы — в конверте `ok`/`error`. Финансовые эндпоинты возвращают финансовые поля только internal-ролям; роли `client` — `FORBIDDEN` либо client-представление без финансов.

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/tasks/{id}/timer/start` | старт таймера (атомарно закрывает предыдущий) → `time.started` |
| `POST` | `/api/tasks/{id}/timer/stop` | стоп таймера → `time.stopped` + постановка пересчёта |
| `GET` | `/api/me/timer` | текущий активный таймер пользователя (если есть) |
| `GET` | `/api/tasks/{id}/cost` | текущая себестоимость задачи (internal-роли) |
| `GET` | `/api/projects/{id}/pnl` | P&L проекта: бюджет, себестоимость, маржа факт vs план (internal-роли) |
| `GET` | `/api/projects/{id}/economics/timeline` | динамика себестоимости/маржи для дашборда |
| `GET` | `/api/alerts` | активные алерты tenant (internal-роли) |
| `POST` | `/api/projects/{id}/margin-threshold` | задать порог маржи проекта (manager/owner) |

## Серверная верификация Этапа 2

```bash
# backend
npm ci && npm run lint
npm run test                # unit: формула, сегментация по ставкам, расчёт маржи, idempotent-raise
npm run test:integration    # с реальными PG/Redis/RabbitMQ: воркер, транзакции, кэш
npm run test:e2e
npm run build
```

Минимальные группы тестов:

| Группа | Минимальные кейсы |
|---|---|
| трекер | старт закрывает предыдущий таймер; два открытых таймера невозможны (нарушение индекса); запрет нулевой/отрицательной длительности |
| формула себестоимости | сумма по сегментам; `time_log` через границу смены ставки разбивается корректно; открытая запись растёт до `now()` |
| идемпотентность | повторная обработка сообщения `economics` не меняет результат и не задваивает стоимость |
| смена ставки | изменение `rates` пересчитывает историю по версиям |
| P&L | `margin_actual` = (бюджет − себестоимость)/бюджет; план vs факт для проекта из сделки |
| алерты | raise при пересечении порога вниз; idempotent (нет дублей активных); auto-resolve при возврате выше порога |
| client-изоляция | роль `client` не получает `cost`/`pnl`/`alert` ни в REST, ни в WebSocket-комнате |
| realtime | `task.cost_changed`/`project.pnl_changed` доходят до internal-ролей и не доходят в клиентские комнаты |
| нагрузка | артефакт: пересчёт под потоком закрытий `time_log` + тики расписания; отсутствие потери/задвоения работы |

Артефакты: список команд и коды выхода; вывод тестов; список миграций; нагрузочный артефакт движка; commit SHA на staging.

Этап 2 принимается только при проходящих тестах идемпотентности, корректности формулы и client-изоляции до нагрузочного smoke. Нагрузочное число без них приёмочным артефактом не является.

## Контрольная точка этапа

По завершении Этапа 2 руководитель видит финансовый вес каждой задачи на канбан-доске в реальном времени, P&L проекта считается в моменте (план vs факт для сделок), а система предупреждает о падении маржи до ухода проекта в минус. Это рабочее финансовое ядро, на которое Этап 3 (AI Standup) подаёт автоматические события трекинга, а Этап 4 (Velocity) — производные метрики из накопленных `time_logs`.
