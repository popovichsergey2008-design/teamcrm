# TEAMCRM Этап 1 — нагрузочный smoke realtime-слоя

Артефакт по Шагу 1.4 (стабилизация и нагрузочная проверка realtime). Харнесс: `realtime-smoke.mjs`
(socket.io-client v4, та же версия, что и сервер). Прогон через **edge nginx** (реальный путь, ws-upgrade)
на staging `109.199.99.13`, в одноразовом `node:20` контейнере на сети стека.

## Сценарий

- `CLIENTS` сокетов подключаются и подписываются на одну комнату проекта (`project.subscribe`);
- `MOVERS` фоновых клиентов непрерывно переносят карточки (`POST /api/tasks/:id/move`);
- `prober` измеряет end-to-end задержку: время от REST-вызова move до прихода `task.moved` в комнату;
- метрики: подключённые сокеты, число перемещений, суммарный fan-out событий, задержка p50/p90/p99.

## Результат (CLIENTS=120, MOVERS=4, DURATION=20s)

| Метрика | Значение |
|---|---|
| Сокеты подключены | **120 / 120** |
| Перемещений выполнено | 600 (ошибок: **0**) |
| Перемещений/сек | 28.8 |
| Событий доставлено | **72 000** = 600 × 120 |
| **Fan-out ratio** | **120 (нулевая потеря событий)** |
| Событий/сек | 3 462 |
| Задержка p50 / p90 / p99 | **87 / 215 / 2675 мс** (55 сэмплов) |

Вывод: WebSocket-слой устойчиво держит 120 одновременных сокетов и доставляет ~3.5k событий/с в общую
комнату без потерь; медианная end-to-end задержка (REST move → доставка всем 120 клиентам) — 87 мс.
p99-выброс (один сэмпл) — кандидат на наблюдение, не блокер.

## Находка (зафиксировано, для оптимизации на Этапе 2)

Первые прогоны вставляли карточку на `position 0`, из-за чего перенос сдвигал ВСЕ строки колонки
(`UPDATE ... position+1 WHERE position >= 0`). Под 4+ конкурентными movers это давало deadlock/serialization
(40P01/40001) и просадку throughput. Исправлено двумя мерами:
1. **Retry на конкурентных конфликтах** в `DbService.withTransaction` (коды 40001/40P01, экспон. бэкофф) —
   корректность под конкуренцией (ошибки 20 → 0);
2. в нагрузочном прогоне перенос на возрастающую позицию (минимальный lock footprint) — изоляция замера
   именно realtime-слоя.

Worst-case «все тянут карточку в начало одной колонки» остаётся write-contention сценарием: на Этапе 2
(где move ещё и триггерит пересчёт себестоимости) стоит рассмотреть менее блокирующую модель позиций
(напр. дробные/lexorank позиции вместо сплошной перенумерации).

## Воспроизведение

```bash
docker run --rm --network teamcrm_crm-net -v /opt/teamcrm/backend:/app -w /app \
  -e BASE_URL=http://crm-edge -e CLIENTS=120 -e MOVERS=4 -e DURATION_MS=20000 \
  node:20-bookworm-slim \
  bash -lc "[ -d node_modules/socket.io-client ] || npm i socket.io-client@4.8.0 --no-save; node loadtest/realtime-smoke.mjs"
```

# Этап 2 — нагрузочный smoke движка economics

Харнесс: `economics-smoke.mjs` (только `fetch`, без зависимостей). Поток закрытий `time_log`
(start/stop по множеству задач) → движок пересчитывает себестоимость в очереди `economics`.
Один активный таймер на пользователя (инвариант БД) → продюсер серийный, нагрузка на стороне
очереди/воркера + тик расписания.

## Результат (TASKS=16, DURATION=20s, INTERVAL=120ms)

| Метрика | Значение |
|---|---|
| Закрытий `time_log` | 89 (ошибок: **0**) |
| Закрытий/сек | 4.4 |
| `cost_actual` после drain | 1554.3 |
| `cost_actual` после форс-пересчёта | 1554.3 |
| **Идемпотентность** | **TRUE** (повторный полный пересчёт не изменил стоимость) |

Вывод: под потоком закрытий движок пересчитывает себестоимость без потери и задвоения работы —
форсированный повторный полный пересчёт даёт идентичный результат (полный recompute из `time_logs`
идемпотентен по построению). 0 ошибок API таймера (инвариант одного активного таймера соблюдён).

## Воспроизведение

```bash
docker run --rm --network teamcrm_crm-net -v /opt/teamcrm/backend:/app -w /app \
  -e BASE_URL=http://crm-edge -e TASKS=16 -e DURATION_MS=20000 \
  node:20-bookworm-slim node loadtest/economics-smoke.mjs
```
