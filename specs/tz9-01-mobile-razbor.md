# ТЗ-9 · Мобильное приложение ANTHILL — разбор пакета и карта готовности бэкенда

Источник: `TZ/TEAMCRM_MOBILE_COMPLETE_DOCUMENTATION/TEAMCRM_MOBILE_COMPLETE/` (мастер-дорожная
карта, общая архитектура offline/API/realtime, ТЗ iOS и Android, функциональные спеки по
чатам/митам/AI и безопасности, чеклист приёмки, 13 волн разработки WAVE_00…WAVE_12).
Разобрано 2026-09-21. Этот документ — не пересказ пакета, а ответ на три вопроса:
что пакет требует от НАШЕГО бэкенда, что там уже есть, чего нет и в каком порядке делать.

---

## 1. Что предлагает пакет — коротко

- Два магазинных приложения (iOS + Android) на **одной кодовой базе React Native + TypeScript**
  (85–95 %), нативные модули Swift/Kotlin только под системные API (Keychain/Keystore,
  APNs/FCM, CallKit/Telecom, ReplayKit/MediaProjection, виджеты, Live Activities, share).
- Главный сценарий — не «CRM в кармане», а «открыл → увидел, что требует решения → ответил /
  назначил / закрыл / созвонился / надиктовал → пошёл дальше». Нижние вкладки:
  Фокус · Проекты · Чаты · Миты · Ещё, плюс глобальная кнопка 🎤.
- **Offline-first** как принцип: SQLite с рабочим набором (не зеркало всей CRM), очередь
  мутаций с идемпотентностью, delta-sync по курсору, политики конфликтов по типам полей
  (сообщения append-only, чек-лист операциями, срок/описание — по версии с показом
  конфликта человеку).
- Push — не источник истины: push → приложение проснулось → delta-sync → экран.
- AI не на телефоне: Mobile → наш бэкенд → AI Gateway; любые пишущие действия ИИ только
  через предпросмотр и подтверждение (совпадает с тем, как сделан AnthillBot в вебе).
- 13 волн: 0 фундамент → 1 auth+оболочка → 2 задачи и «Фокус» → 3 offline → 4 мессенджер →
  5 push+deep links → 6 миты/звонки → 7 AI → 8 системные интеграции → 9 служба заботы →
  10 планшеты → 11 hardening → 12 релиз. MVP = волны 0–2 + куски 4, 5, 7 (login, Фокус,
  задачи, чат задачи, DM, push, deep links, голосовая задача, базовый offline, базовый бот,
  базовые звонки).

## 2. Карта готовности бэкенда

Пакет писался «в общем» и предполагает ручки `/api/mobile/v1/*`. У нас уже есть почти
вся предметная логика — вопрос в мобильных фасадах, а не в фичах.

| Требование пакета | Что есть у нас | Чего не хватает |
|---|---|---|
| Auth: access+refresh, refresh flow, сессии, remote revoke | JWT access+refresh (`/auth/refresh`), сессии с UA/IP, `GET/DELETE /me/sessions` (человек сам), выход | **Отзыв сессии администратором** (остальные отзывы есть только «свои»); код ошибки `SESSION_REVOKED` в ответе; биометрия — чисто клиентская |
| Регистрация устройства `POST /devices/register`, push-токены | Нет | Таблица `mobile_devices` (device_id, platform, push_token, app/os version, last_seen, revoked_at) + ручки |
| Push APNs/FCM (10 типов: задача, согласование, упоминание, сообщение, ответ в ветке, мит скоро, входящий звонок, ответ поддержки, AI готов) | Очередь уведомлений уже есть: письма (Brevo) + **дубль в Telegram** через `TelegramMirror` — все события проходят через одно место (`notifications`) | **Канал push** рядом с почтой и Telegram: провайдер APNs/FCM (или Firebase для обоих), политика приватности (`show_full_preview / sender_only / hide_content`) на организацию, бейджи |
| Deep links: `/projects/:p/task/:t`, `/chats/:id`, `/meetings/:id` | Ровно такие адреса живут в вебе (router.ts) — Universal Links / App Links повесятся на те же URL | AASA-файл и `assetlinks.json` на домене (nginx), отложенная навигация после логина — клиент |
| Мобильный API `/mobile/v1/focus`, `/tasks/:id`, `/chats`, `/sync` | Всё есть по кускам: `/focus`, `/tasks/registry`, `/tasks/:id`, `/chats`, `/chats/:id/messages`, `/nl/*`, `/support/desk/*`, `/media/*`, `/meetings/*` | **Агрегирующие фасады** для первого экрана (Фокус одним запросом), «Что нового» после push. BFF отдельным сервисом не нужен — пакет это и говорит |
| Delta-sync по курсору `POST /sync {cursor}` → изменения | Нет: веб живёт на socket.io + перезапрос | **Журнал изменений** (`change_log`: tenant, entity, id, version, at) + ручка выдачи дельты; версионирование сущностей (`version` у задач, чек-листа, сообщений) |
| Идемпотентность мутаций (`client_request_id`) | Есть только в импортах (по внешнему id) и в поддержке (условные UPDATE) | Заголовок/поле `Idempotency-Key` на POST/PATCH задач, комментариев, сообщений — таблица ключей с TTL |
| Политики конфликтов (версия + условное обновление) | Условные UPDATE есть в поддержке (назначение) и согласованиях; у задач — нет | `If-Match: version` на PATCH задачи/срока/описания → 409 с серверной версией |
| Realtime foreground: `task.updated`, `message.created`, … | socket.io с redis-адаптером, события уже такие (`chat.*`, `support.*`, `task.*`) | Ничего критичного: socket.io-client есть под RN. Отдельный «сырой» WS `/ws/meet` (сигналинг звонков) — тоже подключаем как есть |
| Звонки: пакет предлагает **LiveKit/WebRTC** | У нас **mediasoup + coturn** (свой SFU, TURN, гостевые ссылки, запись, расшифровка, разбор) | НЕ менять SFU: `mediasoup-client` работает в React Native через `react-native-webrtc`. CallKit/Telecom, PiP, ReplayKit/MediaProjection — клиент. Серверу нужно: push «входящий звонок» (VoIP-push на iOS) и тайм-аут звонка |
| AnthillBot: стриминг, отмена, источники, голос | SSE (`text/event-stream`) в `/anthill/ask`, действия с подтверждением, `nl/voice` (длинная надиктовка фоном, `voice_jobs`), `nl/parse-many` | Клиент SSE под RN (fetch-стрим), отмена — уже есть `aborted()`; ничего серверного |
| Voice-to-Smart-Task, несколько задач из записи, предпросмотр | Готово в вебе (`NlCommandModal`: черновики, «Создать все», итоговая страница) | Только клиент |
| Служба заботы: бот первой линии, эскалация, диагностика, созвон по согласию, закрытие человеком | Всё есть (ТЗ-8, 6 этапов + персона первой линии) | Мобильная диагностика — тот же `context` (route/entity/app version/build/device/os/network/request id): расширить allow-list полей контекста на `app_version`, `build`, `device_model`, `network` |
| Файлы: превью, скачивание, вложения offline | MinIO за авторизацией, `/files/:id`, ручки разговоров поддержки | Ничего серверного; локальная очередь загрузок — клиент |
| Version policy `min_supported_version / latest / force_update` | Нет | Ручка `GET /mobile/v1/config` (версии, feature flags) — ~полдня |
| Feature flags server-driven (`mobile_tasks`, `mobile_chat`, …) | Нет общего механизма; есть `platform_settings` (key/value, 0116) | Хранить флаги там же, отдавать в `/mobile/v1/config` |
| Типы из OpenAPI | Swagger уже поднят в `main.ts` | Генерация TS-типов из `/api/docs-json` в репо мобилки — задача клиента |
| Безопасность: только HTTPS, лог без токенов, шифрование локальной БД | HTTPS есть, лимиты частоты в поддержке | Локальная БД, маскирование экранов, jailbreak-сигнал — клиент; серверу — политика организации (нужна ли биометрия, прятать ли текст в push) |

Итог: **предметной логики хватает на MVP уже сегодня**; серверная работа под мобилку —
это пять кусков инфраструктуры: устройства+push, delta-sync с версиями, идемпотентность,
конфиг/флаги/версии, отзыв сессий администратором.

## 3. Где пакет расходится с нашей реальностью — решения

1. **LiveKit → mediasoup.** Пакет рекомендует LiveKit «или WebRTC». Свой SFU уже стоит,
   гостевые комнаты, запись и ИИ-разбор завязаны на него. Переезд ради мобилки — месяц
   работы без пользы человеку. Решение: mediasoup-client в RN. Риск — iOS-фон и CallKit
   с mediasoup требуют аккуратности, но это клиентская работа, не серверная.
2. **Отдельный `/api/mobile/v1/` префикс.** Дублировать 300 ручек не будем. Мобилка ходит
   в те же `/api/*`; под префиксом `/api/mobile/v1/` живут только агрегаты и то, чего в
   вебе нет: `config`, `devices`, `sync`, `focus` (одним запросом).
3. **Push как отдельный канал очереди уведомлений**, а не новая подсистема: у нас все
   события уже сходятся в `notifications` (письмо + Telegram). Push — третий адресат той же
   очереди, с той же логикой «что показывать» (приватность — на организацию).
4. **Delta-sync — самая дорогая серверная часть** (журнал изменений + версии). Делать
   ПОСЛЕ MVP-скелета, но до того, как offline объявят «готовым»: без версий конфликты
   молча перезаписываются, а пакет прямо запрещает «silent data loss».
5. **AnthillBot в поддержке под именем** — уже сделано (персона первой линии), пакет
   пишет «AnthillBot Support» и кнопку «Позвать человека»: в мобилке брать наши тексты
   («Позвать старшего специалиста»), не пакетные.

## 4. Порядок работ (предложение)

Сервер и клиент идут параллельно; серверные куски маленькие и их можно закрыть за
первые волны клиента.

**Сервер, до старта клиентской волны 1 (≈ 3–4 дня):**
- `GET /api/mobile/v1/config` — версии, force_update, feature flags из `platform_settings`;
- `POST/DELETE /api/mobile/v1/devices` — регистрация устройства и push-токена;
- отзыв сессии администратором (`DELETE /team/:userId/sessions/:id`, код `SESSION_REVOKED`);
- AASA / assetlinks на `anthill.team` (nginx + файлы) — deep links работают с первого дня;
- контекст поддержки: поля `appVersion/build/deviceModel/network` в allow-list.

**Сервер под волну 2–3 (≈ 1–1,5 недели):**
- `GET /api/mobile/v1/focus` — «Мне / От меня / На согласовании / Просрочено / Сегодня»
  одним ответом (собирается из существующих сервисов);
- `version` у задач и чек-листов, `If-Match` на PATCH, 409 с серверным значением;
- `Idempotency-Key` на POST/PATCH задач, комментариев, сообщений;
- `change_log` + `POST /api/mobile/v1/sync` (курсор → дельта по рабочему набору).

**Сервер под волну 5 (≈ 1 неделя):**
- канал push в очереди уведомлений (Firebase Cloud Messaging покрывает и APNs, и FCM
  одним SDK; VoIP-push для входящих звонков на iOS — отдельно через APNs);
- политика приватности push на организацию; бейджи (`/nav/counters` уже считает).

**Клиент:** по волнам пакета, MVP = волны 0–2 + чат задачи и DM из 4 + push/deep links из 5
+ голосовая задача и бот из 7 + базовый звонок из 6. Пакет оценок не даёт; по объёму
это отдельная команда на 4–6 месяцев до Production v1 при готовом бэкенде.

## 5. Что нужно решить заказчику до старта

1. **Кто делает клиент** — своя команда RN или подряд; от этого зависит, пишем ли мы
   OpenAPI-контракт первым (для подряда — обязательно).
2. **Имя в магазинах, bundle id / package name, аккаунты Apple Developer и Google Play**
   (заводятся неделями — начинать сразу).
3. **Push-провайдер**: Firebase (проще, один SDK) или прямые APNs+FCM.
4. **Политика биометрии и приватности push по умолчанию** для всех организаций.
5. **Минимальные версии ОС** (предложение: iOS 16+, Android 9 / API 28+).
6. Подтвердить решение **оставить mediasoup** вместо LiveKit.

## 6. Что решено НЕ делать (пока)

- Отдельный BFF-сервис — пакет сам откладывает до роста нагрузки.
- Переезд на LiveKit.
- Полное зеркало CRM в SQLite — только рабочий набор (пакет, разд. 3 архитектуры).
- Волны 8 (виджеты, Live Activities, share) и 10 (планшеты) — после Production v1.

## 7. Решения заказчика (21.09) и что из них следует

1. **Клиент пишем сами.** OpenAPI-контракт первым не нужен — команда одна, ходим в те же `/api/*`.
2. **Магазинов пока нет** — приложения качают с сайта CRM (он в разработке).
   - Android: APK со страницы сайта + проверка обновления в самом приложении — работает.
   - iOS: **без аккаунта Apple Developer ($99/год) поставить приложение людям нельзя вовсе**:
     единственные пути вне App Store — TestFlight (нужен тот же аккаунт; внутренние
     тестеры до 100, внешние до 10 000 после лёгкого ревью) или Ad Hoc (до 100 устройств в
     год по UDID). Enterprise-программа — только для сотрудников одной компании, не для
     клиентов. Решение: аккаунт Apple Developer заводим сразу, раздаём через TestFlight.
3. **Push без потерь.** Push по природе «best effort» — ни Apple, ни Google доставку не
   гарантируют. Потерь не будет не за счёт push, а за счёт устройства системы:
   - источник истины — **серверный ящик уведомлений** (`notifications` уже есть): что не
     доставлено push’ем, приложение забирает при открытии и при восстановлении сети;
   - в приложении на переднем плане — socket.io, как в вебе;
   - push = сигнал «есть новое» с высоким приоритетом + бейдж, тело уведомления по
     политике приватности; после push — delta-sync;
   - входящий звонок на iOS — только через **VoIP-push (PushKit) + CallKit**, иначе
     iOS не покажет звонок в фоне; на Android — FCM high priority + foreground service;
   - провайдер: **Firebase Cloud Messaging** для обеих платформ (на iOS FCM сам ходит в
     APNs) — один SDK, одна очередь; VoIP-push для звонков — напрямую в APNs.
   - Ограничение: Android без сервисов Google (Huawei и т. п.) FCM не получит — там
     остаётся только socket при открытом приложении; это оговариваем на сайте.
4. **Биометрия и приватность — «максимально»:** блокировка Face ID / Touch ID / отпечаток
   включена по умолчанию с порогом «после 5 минут в фоне», организация может ужесточить
   («каждый запуск»); экран прячется в переключателе приложений; push по умолчанию
   показывает только отправителя и тип («Новое сообщение от Глеба»), полный текст —
   по разрешению организации.
5. **Минимальные версии:** iOS 16+, Android 9 (API 28)+ — согласовано.
6. **Звонки: остаёмся на mediasoup.** Практичнее не значит проще: LiveKit дал бы готовый
   RN SDK с CallKit-примерами, но потребовал бы переписать сервер комнат, гостевые ссылки,
   запись и разбор. mediasoup-client + react-native-webrtc — зрелая связка; переподключение
   и CallKit пишем сами, риск снимаем «пробой» в волне 0 (звонок телефон↔веб через TURN).

## 8. Главное требование — «всё, что делается в вебе, само подтягивается в мобилку»

Это меняет архитектуру сильнее, чем всё остальное, и с пакетом (React Native, 13 волн)
прямо конфликтует: в RN каждую функцию веба пришлось бы **делать второй раз** — свои
экраны, свои формы, свой чат. Один разработчик на две версии продукта — это и есть
«потери» в чистом виде.

Два честных пути:

**А. Гибрид: веб-приложение внутри нативной оболочки (Capacitor).**
- Тот же React-фронт, что на сайте, упакован в iOS/Android-приложение; нативные плагины
  дают push (FCM/APNs), биометрию, deep links, share, файлы, микрофон, камеру, бейджи.
- WebRTC (mediasoup) в WKWebView/Android WebView работает — созвоны те же, что в вебе.
- **Обновления веба попадают в приложение сами**: фронт грузится с сервера (или
  подтягивается OTA-обновлением бандла), без пересборки и без магазинов.
- Что теряем против пакета: полноценный offline-first (остаётся уровень PWA — кэш
  экранов, черновики, очередь отправки для сообщений и комментариев), CallKit-уровень
  интеграции звонков (входящий звонок придёт как обычный push, а не как «звонок» на
  экране блокировки), виджеты и Live Activities. Часть этого добирается позже плагинами.
- Что нужно сделать в вебе один раз: **мобильная раскладка** (нижние вкладки на узком
  экране, панель чатов и созвон под телефон) — это же улучшит сайт в телефоне.

**Б. React Native по пакету.**
- Настоящий offline, CallKit, виджеты, «родные» списки.
- Цена: вторая реализация каждого экрана и каждой новой фичи; «само подтягиваться» не
  будет никогда — только общие типы и API-клиент в монорепо.

**Рекомендация: путь А.** Он единственный отвечает требованию «одна разработка — обе
платформы обновляются сами» при одной команде и без магазинов. Пакет остаётся как
карта функций и приёмки (что должно быть в приложении), а не как предписание стека;
волны 3 (offline) и 8 (виджеты) переносятся в «после», волна 6 (звонки) — в объёме
WebRTC-в-WebView без CallKit.

Порядок при пути А:
1. Мобильная раскладка веба (нижние вкладки, чат и созвон под телефон) — нужна в любом
   случае, сайт в телефоне сегодня неудобен.
2. Оболочка Capacitor: iOS + Android проекты, deep links (AASA/assetlinks), биометрия,
   push (FCM), бейджи, share, OTA-обновление бандла, проверка версии/force update.
3. Сервер: `mobile_devices` + push-канал в очереди уведомлений (+ приватность),
   `/api/mobile/v1/config`, отзыв сессии администратором, VoIP-push для звонков.
4. Раздача: страница на сайте (APK + ссылка TestFlight), аккаунт Apple Developer.
5. Потом: PWA-offline (черновики, очередь отправки), CallKit-плагин, виджеты.
