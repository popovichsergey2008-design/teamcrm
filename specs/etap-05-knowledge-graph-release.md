# Этап 5 — Граф знаний, клиентский портал и коммерческий релиз

Этап 5 капитализирует внутренний опыт компании и запускает продажи по SaaS-модели. Граф знаний превращает историю закрытых задач в «корпоративный разум»; клиентский портал даёт прозрачность клиенту, не раскрывая экономику; биллинг и публичный релиз завершают продукт.

Закрывает киллер-фичи master-спеки: **№4 Граф знаний (RAG)** и **№9 Клиентский портал «маржа-сейф»**, и выводит продукт в коммерческий релиз.

Миссия: замкнуть векторный слой (pgvector), заложенный в Этапе 1, — индексировать закрытые задачи, регламенты и комментарии в эмбеддинги; дать диалоговый RAG-поиск с цитатами и строгой изоляцией по tenant **и** по доступу пользователя; агрессивно кэшировать ИИ-ответы; запустить клиентский портал на той же модели данных с client-представлением без финансов; подключить биллинг и метеринг и пройти go-live гейт.

Non-goals / явные границы:

- **парсинг переписок из почты/мессенджеров в сделки** (остаток фичи №6) — пост-v1 расширение, вне коммерческого релиза; формализуется отдельной спекой после запуска;
- движки себестоимости, Velocity и пайплайн дейликов не дублируются — Этап 5 их потребитель/расширитель, не владелец;
- никакого нового realtime/транспорта/брокера — используются существующие (RabbitMQ-очереди `embeddings`, `ai_assist`; Redis-кэш; Socket.io).

## Шаг 5.1. RAG-индексация (векторный слой)

Все закрытые задачи, внутренние регламенты и комментарии к проектам индексируются, превращаются в векторы через embeddings-API и сохраняются в pgvector. Векторный слой заложен с Этапа 1 — здесь он наполняется и обобщается.

### Контракт индексации

- **обобщение векторного слоя.** Таблица `task_embeddings` из Этапа 1 обобщается в единый индекс `knowledge_chunks`, покрывающий несколько типов источников (`task`, `comment`, `regulation`). Существующие task-эмбеддинги мигрируются в новый индекс forward-миграцией;
- **чанкинг.** Длинные документы (регламенты, комментарии) разбиваются на чанки; каждый чанк эмбеддится отдельно; короткая задача — один чанк;
- **эмбеддинг-модель и размерность фиксируются и должны совпадать с размерностью столбца `vector(N)` и HNSW-индекса.** Этап 1 заложил `vector(1536)`; при выборе модели иной размерности — согласовать миграцией индекса (это тот нюанс, что отмечался на контрольной точке Этапа 2);
- **маскирование PII перед эмбеддинг-API** (через модуль `ai`) — egress-правило master применяется к любому тексту, идущему во внешний embeddings-провайдер;
- **триггеры.** Закрытие задачи (`closed_at`) ставит её в очередь `embeddings` (контракт заложен в Этапах 1, 3); создание/обновление регламента и комментария — аналогично;
- **scope доступа в индексе.** Каждый чанк несёт `tenant_id` и `access_scope` (например, `project_id`), чтобы поиск можно было фильтровать не только по арендатору, но и по доступу пользователя;
- идемпотентность: повторная индексация источника заменяет его чанки (по `content_hash`), не плодит дубли.

**DoD шага:** закрытые задачи, регламенты и комментарии индексируются в `knowledge_chunks`; PII маскируется до эмбеддинг-API; чанк несёт tenant и access-scope; повторная индексация идемпотентна.

## Шаг 5.2. «Корпоративный разум» (AI Brain)

Диалоговое окно внутри CRM. Новый сотрудник спрашивает: «Как мы решали проблему с пагинацией на проектах по недвижимости в прошлый раз?» — ИИ анализирует векторную базу, вытаскивает релевантные старые тикеты и выдаёт чёткую пошаговую инструкцию со ссылками на архивы.

### Контракт диалога RAG

Конвейер: `запрос → маскирование PII → эмбеддинг запроса → семантический поиск top-k → сборка контекста → аналитический LLM → ответ с цитатами`.

- **поиск с двойной изоляцией.** Векторный поиск фильтруется по `tenant_id` **и** по access-scope пользователя: пользователь не может извлечь чанки проектов/документов, к которым у него нет доступа. Это инвариант безопасности — RAG не должен стать каналом обхода RBAC;
- **роль `client` не имеет доступа к AI Brain над внутренними знаниями** (внутренний опыт компании — не для клиента);
- **аналитический тир** (`claude-sonnet-4-6` / `claude-opus-4-8`) через модуль `ai`; длинная генерация стримится (SSE/WebSocket);
- **цитаты обязательны.** Ответ ссылается на исходные чанки (задача/документ) — пользователь открывает архивы; ответ без привязки к источникам не отдаётся как «знание»;
- история диалога сохраняется (`brain_conversations`/`brain_messages`) с ссылками на цитированные источники.

**DoD шага:** запрос возвращает пошаговый ответ со ссылками на исходные тикеты; поиск изолирован по tenant и по доступу пользователя; `client` не имеет доступа к внутреннему AI Brain; ответы стримятся.

## Шаг 5.3. Оптимизация ИИ-затрат (Redis caching)

Агрессивное кэширование ИИ-запросов: если сотрудники задают похожие вопросы, ответ отдаётся из Redis без платного запроса к провайдеру (ТЗ, Шаг 5.3).

### Контракт кэша и метеринга

- **кэш ответов в Redis** (контракт master): ключ — нормализованный запрос + `tenant_id` + scope доступа; TTL обязателен;
- **семантический кэш (опционально):** «похожие» вопросы матчатся по близости эмбеддинга запроса в пределах tenant с порогом сходства; при попадании — кэшированный ответ, без вызова LLM;
- кэш строго **tenant- и scope-изолирован**: ответ одного арендатора/доступа не отдаётся другому;
- **метеринг ИИ-затрат** (durable, для биллинга и наблюдаемости): каждый вызов LLM/эмбеддингов пишет `ai_usage` — модель, токены, стоимость, признак cache-hit, tenant; доля cache-hit видна в мониторинге (master → Наблюдаемость).

**DoD шага:** повторяющиеся/похожие запросы обслуживаются из кэша без платного вызова; кэш изолирован по tenant и доступу; ИИ-расход метерится durable.

## Шаг 5.4. Биллинг и публичный релиз

Интеграция платёжных шлюзов для автоматического списания подписки по тарифам (по числу мест или объёму ИИ-токенов). Официальный запуск.

### Контракт биллинга

- **тарифы** (`plans`): лимиты по местам (`seats`) и/или ИИ-токенам, цена, период;
- **подписка** (`subscriptions`): tenant → план, статус, период, счётчики потребления;
- **метеринг:** места — число активных пользователей tenant; ИИ-токены — агрегат из `ai_usage`;
- **лимиты:** мягкие (предупреждение при приближении) и жёсткие (блокировка действия/ИИ-функции при превышении) — поведение по плану;
- **платёжный шлюз** интегрируется через выделенный адаптер; платёжные секреты — только в секрет-менеджере; вебхуки шлюза верифицируются (подпись);
- биллинг scoped по tenant; клиент (`client`) не имеет доступа к биллингу арендатора.

**DoD шага:** подписка по тарифу с метерингом мест и токенов; лимиты применяются; платёжный шлюз и его вебхуки интегрированы и верифицируются.

## Клиентский портал «маржа-сейф» (фича №9)

Клиент видит прогресс, статусы и сроки своего проекта в реальном времени — но **не себестоимость и не маржу**. Одна модель данных, два защищённых представления. Это кульминация сквозного инварианта №9, который закладывался во всех предыдущих этапах.

### Контракт двух представлений

- **единый сериализатор client-представления** — единственный путь отдачи данных проекта/задачи роли `client`; он физически не включает финансовые поля (`cost_current`, `cost_actual`, `margin_actual`, `budget`, ставки, `risk_pct`, Velocity, загрузку);
- **что видит клиент:** название/статус задач и колонок, прогресс проекта, **честную дату/цвет срока** (из Этапа 4 — дата прогноза и светофор без `risk_pct`), свои комментарии;
- **привязка клиента к данным.** Пользователь роли `client` связан с `client_id` (`users.client_id`); портал отдаёт только проекты этого клиента в рамках tenant;
- **client-комнаты WebSocket** получают только нефинансовые события (`task.moved`, статус, изменение даты срока); финансовые события (`task.cost_changed`, `project.pnl_changed`, финансовые рекомендации, алерты маржи) в них не публикуются;
- инвариант проверяется тестами безопасности и в REST, и в WebSocket — на этом этапе финализируется и закрепляется как приёмочный критерий релиза.

**DoD портала:** клиент входит и видит прогресс/статусы/сроки своих проектов; ни одно финансовое поле недоступно ни в REST, ни в WebSocket; клиент видит только проекты своего `client_id`.

## DDL (добавления к Этапам 1–4)

```sql
-- Обобщённый RAG-индекс (поглощает task_embeddings из Этапа 1 forward-миграцией).
CREATE TABLE knowledge_chunks (
    id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id    BIGINT NOT NULL REFERENCES tenants(id),
    source_type  VARCHAR(24) NOT NULL,           -- task | comment | regulation
    source_id    BIGINT NOT NULL,
    chunk_index  INT NOT NULL,
    access_scope BIGINT NULL,                     -- обычно project_id; для фильтра доступа
    content      TEXT NOT NULL,                   -- маскированный текст чанка
    content_hash VARCHAR(64) NOT NULL,            -- идемпотентность переиндексации
    embedding    vector(1536) NOT NULL,           -- размерность = размерности embeddings-модели
    model        VARCHAR(64) NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (tenant_id, source_type, source_id, chunk_index)
);
CREATE INDEX idx_knowledge_hnsw ON knowledge_chunks
    USING hnsw (embedding vector_cosine_ops);
CREATE INDEX idx_knowledge_scope ON knowledge_chunks (tenant_id, source_type, access_scope);

-- Источники знаний: комментарии и регламенты.
CREATE TABLE comments (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id   BIGINT NOT NULL REFERENCES tenants(id),
    project_id  BIGINT NULL REFERENCES projects(id),
    task_id     BIGINT NULL REFERENCES tasks(id),
    author_id   BIGINT NOT NULL REFERENCES users(id),
    body        TEXT NOT NULL,
    is_client_visible BOOLEAN NOT NULL DEFAULT FALSE,  -- для client-представления
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE regulations (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id   BIGINT NOT NULL REFERENCES tenants(id),
    title       VARCHAR(255) NOT NULL,
    body        TEXT NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Диалоги «корпоративного разума».
CREATE TABLE brain_conversations (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id   BIGINT NOT NULL REFERENCES tenants(id),
    user_id     BIGINT NOT NULL REFERENCES users(id),
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE TABLE brain_messages (
    id              BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    conversation_id BIGINT NOT NULL REFERENCES brain_conversations(id),
    role            VARCHAR(16) NOT NULL,         -- user | assistant
    content         TEXT NOT NULL,
    citations       JSONB NULL,                   -- [{source_type, source_id}]
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Durable метеринг ИИ-расхода (для биллинга и наблюдаемости).
CREATE TABLE ai_usage (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id     BIGINT NOT NULL REFERENCES tenants(id),
    feature       VARCHAR(32) NOT NULL,           -- standup_parse | brain | copilot | embedding
    model         VARCHAR(64) NOT NULL,
    input_tokens  INT NOT NULL DEFAULT 0,
    output_tokens INT NOT NULL DEFAULT 0,
    cache_hit     BOOLEAN NOT NULL DEFAULT FALSE,
    cost_estimate NUMERIC(12,4) NOT NULL DEFAULT 0,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_ai_usage_tenant ON ai_usage (tenant_id, created_at);

-- Биллинг.
CREATE TABLE plans (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    code          VARCHAR(48) NOT NULL UNIQUE,
    seats_limit   INT NULL,                        -- NULL = без лимита
    ai_token_limit BIGINT NULL,
    price         NUMERIC(12,2) NOT NULL,
    currency      CHAR(3) NOT NULL DEFAULT 'RUB',
    period        VARCHAR(16) NOT NULL DEFAULT 'monthly'
);
CREATE TABLE subscriptions (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id     BIGINT NOT NULL REFERENCES tenants(id),
    plan_id       BIGINT NOT NULL REFERENCES plans(id),
    status        VARCHAR(16) NOT NULL,            -- active | past_due | canceled
    period_start  TIMESTAMPTZ NOT NULL,
    period_end    TIMESTAMPTZ NOT NULL,
    seats_used    INT NOT NULL DEFAULT 0,
    ai_tokens_used BIGINT NOT NULL DEFAULT 0,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (tenant_id, status) DEFERRABLE INITIALLY DEFERRED  -- один активный план
);

-- Привязка пользователя роли client к заказчику.
ALTER TABLE users
    ADD COLUMN client_id BIGINT NULL REFERENCES clients(id);  -- NOT NULL для роли client
```

Контракты схемы: `knowledge_chunks` несёт `tenant_id` + `access_scope` для двойной изоляции поиска; размерность `vector(1536)` обязана совпадать с эмбеддинг-моделью; `ai_usage` — durable источник для метеринга токенов; `users.client_id` связывает client-пользователя с заказчиком; всё scoped по `tenant_id`.

## Контракт очередей и AI-слоя

| Очередь | Вид работы | Тир |
|---|---|---|
| `embeddings` (из master) | вычисление эмбеддингов источников знаний | embeddings-модель |
| `ai_assist` (из master) | генерация ответов AI Brain (если асинхронно), сводки | аналитический |

AI-контракт (повтор master): единая точка egress — модуль `ai`; маскирование PII перед любым внешним вызовом (LLM/эмбеддинги); тиринг моделей; кэш Redis с tenant/scope-изоляцией; цитаты в RAG-ответах; **изоляция извлечения по tenant и по доступу пользователя** — RAG не обходит RBAC; коммерческие аккаунты провайдеров, нулевое хранение/DPA, размещение по data-residency Этапа 0.

## Realtime / изоляция

| Событие | Видимость client? |

| `task.moved`, статус, изменение даты срока | да (client-представление) |

Артефакты: команды и коды выхода; вывод тестов; список миграций (включая обобщение `task_embeddings` → `knowledge_chunks`); commit SHA на staging; LLM/embeddings/шлюз в тестах замоканы.

Этап 5 принимается только при проходящих тестах изоляции RAG (tenant + доступ) и client-портала (недоступность финансов). Демонстрация графа знаний или портала без этих тестов приёмочным артефактом релиза не является.

## Go-live гейт (коммерческий релиз)

Дополнительно к гейту верификации этапа, перед публичным запуском:

- сквозной прогон всех накопленных наборов тестов Этапов 1–5 на staging;
- подтверждённое решение по data-residency (152-ФЗ / GDPR) и подписанные DPA с LLM/STT-провайдерами (master, Этап 0);
- проверенное восстановление из бэкапа (Этап 0) на полном объёме данных;
- секреты (ключи провайдеров, платёжного шлюза, JWT) — только в секрет-менеджере; отсутствуют в git и ответах API;
- мониторинг, алерты и метеринг ИИ-затрат активны;
- нагрузочный прогон realtime + RAG + движков на целевом профиле.

## Контрольная точка этапа (и продукта)

По завершении Этапа 5 TEAMCRM — это первая CRM, которая сама себя заполняет и показывает реальные деньги по каждой сделке в моменте: воронка, глубина задач, финансовый контроль и проактивный ИИ в одном лёгком интерфейсе. Внутренний опыт компании капитализирован в граф знаний; клиент получает прозрачность без раскрытия экономики; продукт продаётся по SaaS-модели с метерингом мест и ИИ-токенов. Спецификация всех пяти этапов (плюс Этап 0) завершена; пост-v1 расширения (парсинг переписок в сделки, дополнительные интеграции) формализуются отдельными спеками поверх этого фундамента.
