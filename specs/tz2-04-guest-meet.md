# ТЗ-2, Этап 4 — Гостевой доступ в созвон по ссылке (Guest Mode)

Источник: требования клиента от 24.08.2026 — «Клиенту не нужно ничего скачивать или
регистрироваться — он переходит по ссылке прямо в браузере с телефона или компьютера».

Домен решён: ссылки живут на основном домене, `https://teamsmrt.com/meet/<токен>`.
Отдельный `meet.*` не заводим — это DNS, сертификат и второй edge ради косметики.

Из того же обсуждения НЕ входит в этот этап (отдельные спеки): планирование встреч
с `.ics` и напоминаниями, виджет разбора в чат канала, тональность, баланс речи,
закладки на таймлайне.

---

## 1. Что требуется

Внешний человек (клиент, подрядчик, кандидат) заходит в наш созвон, не заводя учётной
записи: открыл ссылку, назвался, попал в разговор. При этом он не получает доступа
ни к чему больше — ни к задачам, ни к чатам, ни к списку сотрудников.

---

## 3. Решения и почему так

**Ссылка привязана к комнате, а не к разговору.** Комнаты сейчас эфемерны, а ссылку
клиенту отправляют заранее — за час, за день. Поэтому при создании ссылки сразу
выделяется постоянный `room_id`, а комната в памяти поднимается по этому id при первом
входе (`MediaService.ensureRoom`). Гость, пришедший раньше всех, не видит ошибки
«созвон не найден» — он видит «встреча ещё не началась».

**Гость всегда ждёт, пока его впустят.** Ссылка может утечь: её перешлют, она попадёт
в переписку, останется в истории браузера. Поэтому вход по ссылке — это не вход в
разговор, а стук в дверь: гость сидит в лобби, сотрудники видят «<имя> просится в
созвон», кто-то из них нажимает «Впустить». Без единого сотрудника в комнате впускать
некому — гость ждёт.

**Гостевой токен — отдельный вид JWT, а не роль пользователя.** Заводить строку в
`users` ради человека из другой компании нельзя: он попадёт в списки сотрудников,
в подсказки исполнителей, в статистику. Поэтому гостевой токен подписан тем же ключом,
но несёт `kind: 'guest'`, свой `gid` и **жёстко зашитый `roomId`** — по нему нельзя
войти в другую комнату, даже зная её id.

**Гость не имеет ни одного HTTP-маршрута, кроме трёх гостевых.** `JwtAuthGuard` его не
пропускает никуда: `kind:'guest'` — не `AccessTokenPayload`. Всё, что ему нужно
(ICE-серверы), отдаётся гостевыми маршрутами.

**Имя гостя в стенограмме — без `speaker_user_id`.** Колонка ссылается на `users(id)`;
попытка записать туда `guest:<uuid>` уронила бы всю расшифровку встречи. Гость
записывается как `speaker` (имя + пометка «гость»), `speaker_user_id = NULL` —
схема это уже допускает.

**Гостю запрещены: приглашение других, управление записью, отзыв ссылок.** Он может
говорить, показывать экран, поднять руку, писать реакции и выйти.

## 4. Модель данных

Миграция `0045_meet_guest_links.sql`:

```sql
CREATE TABLE meet_guest_links (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id   BIGINT NOT NULL REFERENCES tenants(id),
    room_id     VARCHAR(64) NOT NULL,               -- id комнаты SFU (uuid), стабилен
    project_id  BIGINT NULL REFERENCES projects(id),-- проект по умолчанию для задач встречи
    label       VARCHAR(120) NULL,                  -- «ООО Вектор» — для кого ссылка
    token_hash  VARCHAR(255) NOT NULL UNIQUE,       -- храним ТОЛЬКО хэш, как в invite_links
    created_by  BIGINT NOT NULL REFERENCES users(id),
    expires_at  TIMESTAMPTZ NOT NULL,               -- по умолчанию +24 часа
    revoked_at  TIMESTAMPTZ NULL,
    max_uses    INT NULL,
    uses        INT NOT NULL DEFAULT 0,
    last_used_at TIMESTAMPTZ NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Гостей как строк не храним: гость — это `gid` внутри токена и запись в журнале
диагностики (`diag_events`, scope `meet`), где и так лежит вся лента созвона.

## 5. Протокол

**HTTP (гостевые, `@Public`):**

| Маршрут | Ответ |
|---|---|
| `GET /api/meet/guest/:token` | `{ ok, orgName, label, roomActive, hostPresent }` либо `{ ok:false, reason:'expired'\|'revoked'\|'used-up'\|'unknown' }`. Ничего сверх названия организации не отдаём |
| `POST /api/meet/guest/:token/join` `{name}` | `{ token, roomId, iceServers }` — гостевой JWT на 4 часа; `uses+1` |

**HTTP (сотрудник):** `POST /api/meet/guest-links` `{roomId?, projectId?, label?, ttlHours?}` →
`{ id, url, expiresAt }` (полная ссылка отдаётся один раз); `GET /api/meet/guest-links` —
активные ссылки организации; `DELETE /api/meet/guest-links/:id` — отзыв.
Если `roomId` не передан, выделяется новый — это «переговорная под ссылку».

**WebSocket — добавка к существующим 17 сообщениям:**

| Сообщение | Направление | Смысл |
|---|---|---|
| `meet.guest-waiting` | сервер → гостю | в комнате нет сотрудников, ждите |
| `meet.guest-knocking` | сервер → сотрудникам | `{guest_id, name}` — просится войти |
| `meet.guest-admit` | сотрудник → серверу | `{guest_id}` впустить |
| `meet.guest-reject` | сотрудник → серверу | `{guest_id}` отказать (сокет гостя закрывается) |
| `meet.guest-admitted` | сервер → гостю | впустили, дальше обычный протокол входа |

## 6. Шаги

**Ш1. Комната по стабильному id.** `MediaService.ensureRoom(tenantId, roomId, projectId)` —
поднять роутер под заданным id, если такой комнаты нет; вернуть существующую, если есть.
Проверка `tenantId` обязательна: комната чужой организации не отдаётся никогда.

**Ш2. Ссылки.** Миграция, `MeetGuestService` (создание с хэшем токена, разбор, проверки
срока/отзыва/лимита), контроллер с тремя маршрутами сотрудника и двумя гостевыми.
Токен — 32 случайных байта в base64url; в БД `sha256`.

**Ш3. Гость в шлюзе.** `authenticate()` различает два вида токена; `Client` получает
`isGuest`, `guestName`, `roomId`; `userId` гостя — `guest:<gid>`. Лобби: гость после
`meet.join` не входит в комнату, а попадает в `pending`-список комнаты; впуск/отказ по
новым сообщениям; выход и обрыв связи чистят лобби. Запреты для гостя: `meet.invite`,
`meet.record-start`, `meet.record-stop`, `meet.guest-admit/reject`.

**Ш4. Запись и стенограмма.** В `ingestCallRecording` — `speakerUserId = null` для
дорожек гостей, `speaker` = «Имя (гость)». Владелец файла дорожки уже берётся из
`actorId`, менять не нужно.

**Ш5. Экран гостя.** Страница `/meet/<токен>` вне оболочки: проверка ссылки, ввод имени,
проверка микрофона/камеры, «Постучаться», ожидание, затем созвон. Мобильная вёрстка —
обязательна: клиент заходит с телефона.

**Ш6. Хозяин.** В `CallPanel`: кнопка «Ссылка для гостя» (создать и скопировать),
плашка «<имя> просится в созвон» с «Впустить»/«Отказать», пометка «Гость» у участника.

**Ш7. Проверки.** e2e на жизненный цикл ссылки: создание → гость входит → повтор после
отзыва → после срока → сверх лимита → чужая организация. Юнит на разбор и проверку
токена. Шлюз и SFU автотестами не покрываем: `mediasoup` лежит в `optionalDependencies`
и на CI не ставится — проверка живая, по чек-листу ниже.

---

## 7. Безопасность

- В базе только хэш токена; полная ссылка показывается один раз при создании.
- Срок по умолчанию 24 часа, максимум 30 суток; отзыв мгновенный, активный гость
  выкидывается из комнаты.
- Вход только через впуск сотрудником; тихо войти нельзя.
- Гостевой токен привязан к одной комнате и живёт 4 часа.
- Появление гостя видно всем в комнате — отдельным сообщением и пометкой в списке.
- Гость не проходит `JwtAuthGuard` ни на одном обычном маршруте API.

---

## 8. Живая проверка (то, что автотесты не покажут)

1. Гость с **iPhone, Safari** — приоритет: это единственный движок на iOS и самое
   вероятное место, где WebRTC поведёт себя не так.
2. Гость из мобильной сети (не Wi-Fi) — путь через TURN.
3. Гость + запись с ИИ: в стенограмме гость отдельным спикером, разбор не падает.
4. Отзыв ссылки при госте в комнате.
5. Гость пришёл раньше хозяина; хозяин пришёл и впустил.
