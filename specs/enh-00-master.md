# TEAMCRM — Спецификация улучшений v1 (Enhancements v1)

> Отдельный трек поверх реализованных Этапов 1–4 (см. [master.md](master.md)). Это **не** новый этап роадмапа (Этап 5 — RAG/портал/биллинг — отложен), а доработка уже работающего продукта по запросу заказчика. Все контракты master-спеки (NestJS-владение, tenant-scope, JWT/RBAC, API-конверт `ok/error`, Socket.io, фича №9 «маржа-сейф», маскирование PII) остаются в силе и обязательны.

## Цель

Довести до продакшн-качества три области, по которым сейчас минимальный UX:

1. **Личный кабинет пользователя** — управление своим профилем, паролем, аватаром, уведомлениями, доступностью и безопасностью (сессии/2FA).
2. **Управление командой** — добавление сотрудников, должности (справочник), группы/отделы (плоские), назначение ролей/должностей/групп, деактивация.
3. **Карточка задачи как в Bitrix24 (или лучше)** — полноценное название и rich-text описание, вложения (файлы), комментарии + история изменений, чеклисты, метки, приоритет, наблюдатели.

## Зафиксированные продуктовые решения (вход от заказчика)

| Решение | Выбор |
|---|---|
| Оргструктура и права | 4 фиксированные RBAC-роли (owner/manager/member/client) **сохраняются**; добавляются **должности** (справочник) и **плоские группы/отделы** (без вложенности) |
| Хранилище файлов | **MinIO** (S3-совместимое) — отдельный контейнер в стеке; доступ через backend (presigned URL / проксирование), access-control по tenant |
| Карточка задачи | название + rich-text описание, вложения, комментарии+история, чеклисты, метки, приоритет, наблюдатели — **полный набор** |
| Личный кабинет | профиль+смена пароля, аватар, уведомления+доступность, безопасность (сессии/2FA) — **полный набор** |

## Текущее состояние (от чего отталкиваемся)

Реализовано и работает на staging (`109.199.99.13`), миграции применены до `0005`:

- `users`: `id, tenant_id, email, password_hash, full_name, role_id, is_active, weekly_capacity_hours`. Нет: должности, аватара, телефона, таймзоны, настроек уведомлений, `client_id`.
- `roles`: owner/manager/member/client. RBAC через `@Roles(...)` + `RolesGuard`; tenant-scope через JWT.
- `UsersModule`: `POST /api/users` (создать сотрудника), `GET /api/users` (список). Нет редактирования профиля, должностей, групп.
- Auth: register/login/refresh/logout/`GET /api/me`. `refresh_tokens` (token_hash/expires_at/revoked_at) — основа для списка сессий.
- `tasks`: `title, description (TEXT, есть в БД но в UI почти не редактируется), assignee_id, status, is_blocked, estimate_hours, deadline_at, predicted_finish_at, risk_*, closed_at, cost_current`. Нет: приоритета, меток, наблюдателей, комментариев, вложений, чеклистов, истории.
- Инфраструктура: Docker Compose (postgres+pgvector, redis, rabbitmq, crm-api, crm-web, edge nginx, observability), CI/CD (GitHub Actions → автодеплой на staging). Очередь `notifications` уже объявлена.

## Архитектурные принципы трека (обязательны)

- **Только forward-миграции**, нумерация продолжается с `0006`. Откат — встречной миграцией.
- **tenant-scope везде**: каждая новая таблица несёт `tenant_id`; репозитории фильтруют по tenant из JWT.
- **RBAC**: управление командой/должностями/группами — `owner`/`manager`; редактирование своего профиля — любой internal-пользователь себя; роль `client` к внутренним данным не допускается.
- **Фича №9 сохраняется**: новые поля задачи (комментарии с флагом `is_client_visible`, вложения, метки) проектируются с учётом будущего client-портала; финансовые поля не протекают.
- **Единая точка egress** к внешним сервисам (если понадобится антивирус/превью) — не вводим без необходимости. Загрузка файлов проходит валидацию типа/размера.
- **Реалтайм** — существующий Socket.io: новые доменные события (`task.comment_added`, `task.updated`, `task.attachment_added`, и т.п.) идут в комнаты проекта по тем же правилам изоляции.
- **API-конверт** `ok/error`, Swagger из контроллеров, секреты (MinIO-ключи) только в `.env`/секрет-менеджере.

## Роадмап работ (этапы и порядок)

Порядок продиктован зависимостями: файловое хранилище — фундамент для аватаров (кабинет) и вложений (карточка); должности нужны и кабинету (поле профиля), и команде.

| Этап работ | Документ | Зависит от | Содержание |
|---|---|---|---|
| **A. Файловое хранилище** | enh-01 | — | MinIO в стек, модуль `files`, загрузка/скачивание, access-control, валидация |
| **B. Команда и должности** | enh-03 | — (частично A для будущего) | справочник должностей, группы/отделы, участники, приглашение/управление |
| **C. Личный кабинет** | enh-02 | A (аватар), B (должность) | профиль, пароль, аватар, уведомления, доступность, сессии/2FA |
| **D. Карточка задачи** | enh-04 | A (вложения) | rich-описание, вложения, комментарии+история, чеклисты, метки, приоритет, наблюдатели |

> Этапы B и C тесно связаны (должность — общее поле); допускается их слияние в один блок реализации. D — самый крупный, разбит на под-этапы внутри своего документа.

## Доктрина верификации (для каждого этапа работ)

Сохраняется доктрина master/Этапов 1–4:

- unit — чистая логика (валидация, сериализаторы представлений, права);
- integration — с реальными PostgreSQL/Redis/RabbitMQ/MinIO (через Docker);
- e2e — ключевые потоки (загрузка файла, смена пароля, добавление сотрудника в группу, комментарий/вложение/чеклист в задаче);
- security — tenant-изоляция новых сущностей; недоступность чужих файлов; RBAC на управлении командой; неизменность фичи №9 (client не получает финансы и приватные комментарии);
- CI/CD: каждый этап проходит существующий пайплайн (lint → unit → e2e на сервис-контейнерах → автодеплой на staging). MinIO добавляется как сервис-контейнер в CI.

Каждый этап работ принимается только при зелёном CI и пройденных security/изоляционных тестах. Демонстрация UI без этих тестов приёмкой не является.

## Non-goals трека

- RAG/граф знаний, клиентский портал как продукт, биллинг (это Этап 5 роадмапа — отложен).
- Внешняя интеграция почты/мессенджеров, парсинг переписок в сделки (пост-v1).
- Сложная иерархия отделов (дерево), кастомные роли с granular-permission-matrix — сознательно вне scope (выбран вариант «должности + плоские группы»); может быть отдельным треком позже.
- Видеозвонки/чат реального времени сверх комментариев к задачам.

## UI-переключатели и локализация (2026-06-30)

- **Монетизация (временно скрыта).** Флаг `frontend/src/config.ts → MONETIZATION_ENABLED = false` прячет в UI всё, что связано с деньгами: P&L-панель проекта (бюджет/себестоимость/маржа) и алерт маржи на доске, бейдж себестоимости `₽` на канбан-карточках и в карточке задачи, ставку `₽/час` сотрудника в «Команде». Бэкенд (Этап 2: тайм-трекер/себестоимость, RabbitMQ-воркер, P&L) НЕ тронут — вернуть отображение = поставить флаг `true`. Метрики Velocity/загрузка (не деньги) остаются.
- **Локализация ролей.** Уровни доступа выводятся по-русски через `frontend/src/lib/labels.ts → roleLabel`: owner→Владелец, manager→Руководитель, member→Сотрудник, client→Клиент. Сами коды ролей и RBAC не меняются (4 уровня, на них завязана безопасность). Селекты роли в «Команде» используют `ASSIGNABLE_ROLES` (owner/manager/member).
