## Позиционирование

TEAMCRM — «AI-Driven партнёр для бизнеса». Продукт смещает фокус с ручного контроля и заполнения отчётов на автоматический сбор данных и предиктивную аналитику. Ключевая незанятая ниша рынка (см. конкурентный анализ): пересечение сильного **проектного управления** с **финансами/юнит-экономикой в реальном времени** и **проактивным ИИ**, локализованное под рынок СНГ.

Слоган-инвариант: **CRM, которую не нужно заполнять руками** — данные актуальны, потому что система наполняет себя сама.

### Киллер-фичи (продуктовые инварианты)

Каждая фича ниже — это продуктовый инвариант, на который опираются контракты этой спеки. Номера соответствуют ТЗ.

| № | Фича | Инвариант |
|---|---|---|
| 1 | Real-Time Unit-Economics | каждая задача имеет себестоимость, пересчитываемую в реальном времени из фактически затреканного времени и ставок |
| 2 | AI Standup Pipeline | голосовой дейлик в Telegram → транскрипция → извлечение структурированного JSON → авто-обновление доски и тайм-трекинга |
| 3 | AI Load Balancer | расчёт Velocity сотрудника и предупреждение о перегрузе до назначения задачи |
| 4 | Граф знаний (RAG) | база опыта из истории закрытых задач; диалоговый «корпоративный разум» |
| 5 | Сквозная маржа Deal → Project | выигранная сделка разворачивается в проект; плановая маржа сверяется с фактической себестоимостью в реальном времени |
| 6 | Self-Filling CRM | авто-тайм-трекинг, авто-перенос карточек, парсинг переписок — минимум ручного ввода |
| 7 | Проактивный ИИ-операционист | ИИ инициирует действия (перераспределение, предупреждение о риске), а не ждёт запроса |
| 8 | Светофор честных сроков | дедлайн считается из реальной Velocity и текущей загрузки, пересчитывается с цветовой индикацией риска |
| 9 | Клиентский портал «маржа-сейф» | одна модель данных, два защищённых представления: клиент видит прогресс и сроки, но не себестоимость и маржу |

Инвариант безопасности фичи №9 — **сквозной**: любой контракт чтения данных обязан различать internal-представление (с финансами) и client-представление (без них). См. [Multi-tenancy и RBAC](#multi-tenancy-и-rbac).

## Технологические контракты

Эти решения зафиксированы. ТЗ предлагает альтернативы («NestJS или Laravel», «React или Vue», «pgvector либо Pinecone») — спека коммитится в конкретику; реализация не выбирает стек заново.

| Слой | Технология | Примечание |
|---|---|---|
| Backend | **NestJS** (Node.js LTS, TypeScript) | модульная структура, единый язык с фронтендом |
| Frontend | **React** (SPA, TypeScript) | собственная дизайн-система, без тяжёлого UI-фреймворка с «мусорными» модулями |
| Реляционная БД | **PostgreSQL** | source of truth для бизнес-данных; ACID обязателен для финучёта |
| Векторный слой | **pgvector** (расширение PostgreSQL) | эмбеддинги, HNSW-индексы; единый инстанс БД, без внешней векторной зависимости |
| Кэш / acceleration | **Redis** | кэш аналитики, ИИ-ответов, pub/sub для realtime fan-out, rate-limit |
| Брокер очередей | **RabbitMQ** | durable-очереди для фоновых задач (расчёт себестоимости, ИИ-пайплайн, эмбеддинги) |
| Realtime | **Socket.io** поверх NestJS WebSocket Gateway | комнаты по проектам, авторизация сокетов |
| Аутентификация | **JWT** (access + refresh) + **RBAC** | tenant scope в каждом токене |
| Контейнеризация | **Docker + Docker Compose** | инфраструктура как код, окружения dev/staging/prod |
| LLM-провайдеры | **Anthropic** (primary) и/или OpenAI | гибридный тиринг моделей; см. [AI-слой](#ai-слой) |
| Speech-to-Text | **OpenAI Whisper API** | транскрипция голосовых дейликов |

Принцип владения: каждый слой имеет единственного владельца. Позднейшие этапы расширяют владельца, но не вводят параллельный runtime, очередь, транспорт или UI с дублирующим владением. React-фронтенд — progressive enhancement поверх API: он не владеет доменной моделью и не обращается напрямую к БД, Redis, RabbitMQ или LLM-провайдерам.

## Доменная модель

Доменные сущности и их связи — каноничны. Физическая схема (DDL) определяется в [Этапе 1](etap-01-foundation.md); здесь — смысл и инварианты.

| Сущность | Назначение | Ключевые инварианты |
|---|---|---|
| `tenant` (организация) | арендатор SaaS | корень изоляции данных; всё ниже scoped по `tenant_id` |
| `user` | сотрудник/пользователь | принадлежит одному tenant; имеет роль (RBAC) |
| `role` | роль в рамках RBAC | определяет доступ к действиям и к финансовому представлению |
| `client` | заказчик проекта | имеет доступ только к client-представлению своих проектов (фича №9) |
| `rate` | почасовая ставка | привязана к user (и/или роли); версионируется по времени — себестоимость считается по ставке, актуальной на момент трекинга |
| `deal` | сделка в воронке | имеет стадию, сумму, плановую маржу; разворачивается в `project` (фича №5) |
| `project` | проект | бюджет, клиент, плановая vs фактическая маржа (P&L) |
| `task` | задача на канбан-доске | статус (колонка), исполнитель, оценка, **денежная себестоимость в реальном времени** (фича №1) |
| `time_log` | запись трекинга | `timestamp_start`, `timestamp_end`, user, task; основа фактической себестоимости |
| `task_embedding` | эмбеддинг закрытой задачи | вектор pgvector; основа графа знаний (фича №4) |
| `velocity_metric` | производная метрика | чистая скорость сотрудника; основа балансировщика и честных сроков (фичи №3, №8) |
| `alert` / `notification` | событие/уведомление | блокеры, риск срыва, перегруз — каналы проактивного ИИ (фича №7) |

Инварианты:

- **Финансовый учёт ACID.** Любая мутация `time_log`, `rate`, бюджета проекта и расчёт себестоимости происходят в транзакции PostgreSQL. Себестоимость не хранится как «истина» в Redis — Redis только кэширует производное представление.
- **Эмбеддинги закладываются с первого этапа.** При закрытии задачи её эмбеддинг ставится в очередь на вычисление немедленно. Без этого граф знаний (Этап 5) по исторической базе будет невозможен — это требование ТЗ (Этап 1, Шаг 1.1).
- **Время фиксируется фактом, не вводом.** `time_log` создаётся из событий «В работу / Пауза», а не из ручного ввода «я работал N часов».

## Архитектурные контракты

Этот раздел фиксирует технические границы. Контракты обязательны для кода, миграций и UI; продуктовые описания фич выше остаются поведенческими ориентирами.

### Гибридное хранилище

PostgreSQL — durable source of truth. Векторный слой (pgvector) живёт в том же инстансе PostgreSQL отдельными таблицами с HNSW-индексами. Redis — acceleration layer; потеря Redis не должна терять данные или работу.

Разделение ответственности:

| Хранилище | Владеет |
|---|---|
| PostgreSQL | бизнес-данные, финучёт, time logs, ставки, статусы задач, эмбеддинги (pgvector) |
| Redis | кэш аналитики (P&L, дашборды), кэш ИИ-ответов, presence/pub-sub для realtime, rate-limit-счётчики, краткоживущие locks |
| RabbitMQ | durable-сообщения фоновых задач; не является source of truth — состояние всегда восстановимо из PostgreSQL |

Кэш в Redis всегда имеет TTL и инвалидируется при мутации источника. Любое значение в Redis должно быть пересчитываемо из PostgreSQL.

### Realtime контракт (WebSocket)

Канал — Socket.io поверх NestJS Gateway. Реалтайм критичен для командной работы: перенос карточки, смена исполнителя, изменение себестоимости отображаются у всех участников проекта мгновенно, без перезагрузки.

Правила:

- сокет авторизуется тем же JWT, что и REST; неавторизованный сокет не входит ни в одну комнату;
- комнаты — по `project_id` (плюс tenant scope); пользователь получает события только тех проектов, к которым у него есть доступ;
- **клиентские сокеты получают только client-представление** (фича №9): события с себестоимостью/маржой не публикуются в клиентские комнаты;
- горизонтальное масштабирование — через Redis-адаптер Socket.io (pub/sub); состояние presence в Redis;
- WebSocket — транспорт уведомлений о доменных событиях, не альтернативный путь записи. Любая мутация идёт через авторизованный API/command path, затем эмитится событие.

Минимальный набор доменных событий: `task.moved`, `task.updated`, `task.cost_changed`, `task.blocked`, `deal.converted`, `alert.raised`.

### Unit-Economics движок (контракт расчёта)

Себестоимость задачи — производная величина, пересчитываемая фоновым воркером.

Формула (ТЗ, Шаг 2.2):

```
Текущая_стоимость_задачи = Σ ( затреканные_секунды / 3600 × почасовая_ставка_исполнителя )
```

Контракт:

- расчёт выполняется фоновым воркером (RabbitMQ), запускаемым по событию закрытия `time_log` и по расписанию (догоняющий пересчёт);
- ставка берётся версионная — действовавшая на момент интервала трекинга, а не текущая;
- результат пишется денормализованным полем задачи (`task.cost_current`) в транзакции и кэшируется в Redis для дашбордов;
- P&L проекта = бюджет − Σ себестоимостей задач проекта; при падении маржи ниже порога (например, 20%) поднимается `alert` (фича №5: ловить убыточные сделки до закрытия проекта);
- любая запись себестоимости идемпотентна по `(task_id, расчётный_снэпшот)` — повторный пересчёт не задваивает данные.

### Очереди и фоновые воркеры

RabbitMQ — единый брокер фоновой работы. Классы задач (resource classes / очереди) разделены по нагрузочному профилю:

| Очередь | Назначение |
|---|---|
| `economics` | пересчёт себестоимости задач и P&L проектов |
| `embeddings` | вычисление эмбеддингов закрытых задач (pgvector) |
| `ai_standup` | пайплайн голосовых дейликов (Whisper → LLM → применение) |
| `ai_assist` | проактивные ИИ-действия, скоринг, сводки |
| `notifications` | доставка уведомлений и алертов |

Правила: воркеры идемпотентны, сообщение не является durable-состоянием (источник — PostgreSQL), при падении воркера задача переобрабатывается без двойного применения. Долгие/дорогие ИИ-вызовы выполняются только из воркеров, не в HTTP-цикле запроса.

### AI-слой

LLM-вызовы инкапсулированы в выделенном модуле NestJS. Сценарные шаги (фронтенд, контроллеры) не вызывают LLM-провайдера напрямую.

**Гибридный тиринг моделей** (ТЗ, раздел 4) — минимизация затрат:

| Класс | Модель (актуальные id) | Применение |
|---|---|---|
| дешёвый/быстрый | `claude-haiku-4-5` (Anthropic) или сопоставимый OpenAI | массовая рутина: парсинг голосовых дейликов, извлечение JSON-намерений |
| аналитический | `claude-sonnet-4-6` / `claude-opus-4-8` (Anthropic) | сложные задачи: сводки для CEO, сборка графа знаний, проактивные рекомендации |

> Model id выверены по справочнику Claude API на дату написания спеки. При реализации использовать актуальные id из справочника, не хардкодить устаревшие алиасы.

**Слой анонимизации (Data Masking)** — обязателен перед отправкой текста во внешний LLM/Whisper: бэкенд маскирует телефоны, e-mail, пароли и иные PII регулярными выражениями, заменяя плейсхолдерами. Маскирование — единая точка на выходе AI-модуля; обойти его шаги не могут.

**Кэширование ИИ-ответов (Redis)** — для повторяющихся/похожих запросов (фича №4, Шаг 5.3): ответ отдаётся из Redis без платного запроса к провайдеру. Кэш ключуется по нормализованному запросу + tenant scope, имеет TTL.

**RAG-контракт (граф знаний, Этап 5):** закрытые задачи, регламенты и комментарии индексируются в эмбеддинги (pgvector). Диалоговый запрос → семантический поиск top-k → передача контекста аналитической модели → ответ со ссылками на исходные тикеты.

**Юридический контракт:** запросы идут только через коммерческие API-аккаунты провайдеров; данные по умолчанию не используются для обучения публичных моделей; сроки хранения и опции нулевого хранения фиксируются в DPA под конкретного провайдера. Решение по data-residency (152-ФЗ для РФ / GDPR для ЕС-Украины) принимается на [Этапе 0](etap-00-infrastructure.md) и распространяется на размещение LLM-трафика.

### API envelope

Все ответы API имеют единый конверт:

```json
{ "ok": true, "data": {}, "meta": {} }
```

```json
{ "ok": false, "error": { "code": "VALIDATION_FAILED", "message": "human-safe message", "details": {} } }
```

Минимальные коды ошибок:

| Код | Значение |
|---|---|
| `VALIDATION_FAILED` | вход отклонён до мутации |
| `UNAUTHORIZED` | нет/невалиден JWT |
| `FORBIDDEN` | валидная авторизация, но нет прав/чужой tenant |
| `NOT_FOUND` | сущность не видна пользователю |
| `CONFLICT` | конфликт версий/состояния |
| `RATE_LIMITED` | превышен лимит запросов |
| `INTERNAL` | внутренняя ошибка с безопасным сообщением |

UI никогда не показывает секреты (токены провайдеров, ключи, raw payload credentials). Документация API — Swagger/OpenAPI, генерируется из контроллеров.

### Multi-tenancy и RBAC

- **Tenant scope** присутствует во всех бизнес-таблицах (`tenant_id`) и в JWT. Любой запрос чтения/записи фильтруется по tenant из токена; кросс-tenant доступ невозможен на уровне репозиториев.
- **RBAC**: роли определяют доступ к действиям и — критично — к **финансовому представлению**. Минимальный набор ролей: `owner`, `manager`, `member`, `client`.
- **Два представления одной модели (фича №9):** контракт чтения данных проекта/задачи различает `internal` (с себестоимостью, маржой, ставками) и `client` (прогресс, статусы, сроки — без финансов). Роль `client` физически не может получить финансовые поля ни через REST, ни через WebSocket. Это проверяется тестами безопасности.

### Наблюдаемость

- Мониторинг метрик и логов (Prometheus + Grafana или Netdata; централизованные логи через Loki) — поднимается на [Этапе 0](etap-00-infrastructure.md).
- Каждый фоновый расчёт (себестоимость, эмбеддинг, ИИ-пайплайн) логируется: вход, результат, время, диагностика ошибок и retry.
- ИИ-затраты трекаются: число вызовов, токены, доля cache-hit, разбивка по тирам моделей.

### Безопасность данных

- Доступ к серверам — только по SSH-ключам; root-логин отключён; fail2ban; firewall (ufw); TLS (Let's Encrypt); VPN для админ-доступа (Этап 0).
- Секреты (ключи провайдеров, пароли БД, JWT-секрет) — только в переменных окружения / секрет-менеджере, никогда в git и не в ответах API.
- PII маскируется перед отправкой во внешние LLM/STT (см. AI-слой).
- Data-residency (152-ФЗ / GDPR) — архитектурное решение Этапа 0, влияющее на размещение БД и LLM-трафика; миграция персональных данных между юрисдикциями после запуска недопустима без юридической проработки.

### Testing doctrine

Тесты — обязательный артефакт каждого реализованного поведения, не опция.

Минимальные классы тестов:

- unit — чистая логика (расчёт себестоимости, парсер JSON-намерений ИИ, расчёт Velocity, маскирование PII);
- интеграционные — с реальными PostgreSQL/Redis/RabbitMQ (через Docker);
- транзакционные — идемпотентность пересчёта, отсутствие двойного применения;
- realtime — синхронизация доски между клиентами, изоляция клиентских комнат от финансовых событий;
- безопасность — изоляция tenant, недоступность финансовых полей роли `client` (REST и WebSocket);
- нагрузочные — realtime-слой и расчётный движок (k6 / Artillery), особенно перед Этапом 2;
- E2E — ключевые пользовательские потоки (вход по роли, перенос карточки, разворот сделки в проект).

Happy-path-only набор тестов приёмкой не считается. Если поведение нельзя автоматизировать на текущем этапе — это фиксируется в артефакте этапа с обоснованием и указанием, какой этап закрывает пробел.

## Roadmap этапов

Этапы — упорядоченные контракты поставки. Поздний этап расширяет владельцев ранних, не вводя параллельные runtime/очереди/транспорт/UI.

Контрольная точка после Этапа 1: пользователи входят по ролям, видят канбан-доску и переносят карточки в реальном времени, а база уже умеет хранить эмбеддинги — фундамент, на который без переделок ложится финансовое ядро Этапа 2.

### Гейт верификации на каждом этапе

- этап завершается полной серверной проверкой реализованной поверхности до начала следующего;
- проверка включает все накопленные к этапу unit/интеграционные/транзакционные/realtime/security-наборы плюс negative/edge/concurrency-кейсы этапа;
- после появления нагрузочной инфраструктуры каждый следующий этап перегоняет релевантный нагрузочный поднабор;
- артефакты верификации: список команд, commit SHA, окружение, длительность, метрики, падения;
- приёмка по Definition of Done этапа; happy-path без negative/edge/security приёмкой не является.
