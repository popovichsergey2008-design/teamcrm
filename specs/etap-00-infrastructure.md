# Этап 0 — Инфраструктура и сервер

Этап 0 готовит безопасную, воспроизводимую и наблюдаемую среду **до написания первой строки бизнес-логики**. ТЗ выносит его в отдельную фазу намеренно: пропуск этого этапа оплачивается простоями и инцидентами безопасности.

Миссия: поднять окружения dev/staging/prod как код, захардненный периметр, ядро хранилищ (PostgreSQL+pgvector, Redis, RabbitMQ), CI/CD с автодеплоем на staging, мониторинг и бэкапы с протестированным восстановлением.

Non-goals этапа:

- никакой бизнес-логики, доменных моделей или API сверх health-check;
- никакого фронтенд-приложения сверх статической заглушки;
- никаких ИИ-интеграций (ключи провайдеров заводятся как секреты, но не используются).

## Шаг 0.1. Инфраструктура и окружения

Выбор площадки с учётом data-residency:

- **РФ** — локализация персональных данных по 152-ФЗ (Selectel, Yandex Cloud, VK Cloud);
- **Украина / ЕС** — провайдеры с GDPR-совместимостью (Hetzner, AWS eu-*).

Решение по data-residency принимается **до старта** и фиксируется в этой спеке: миграция персональных данных между юрисдикциями после запуска болезненна и юридически рискованна. Это же решение определяет допустимое размещение LLM-трафика (см. master → AI-слой).

Проектируются три окружения: **dev**, **staging**, **production**. Конфигурация окружений различается только значениями (секреты, ресурсы, домены), но не структурой — структура общая и описана как код.

| Окружение | Назначение | Деплой |
|---|---|---|
| dev | локальная разработка | `docker compose up` из репозитория |
| staging | предпрод, автодеплой из CI | push в ветку → автосборка → деплой |
| production | боевое | контролируемый релиз |

## Шаг 0.2. Безопасность и периметр

- Хардненинг ОС (Ubuntu LTS): отдельные пользователи, доступ только по SSH-ключам, отключение входа под root, `fail2ban`, автоматические security-обновления.
- Firewall (`ufw`): открыты только нужные порты.
- Reverse proxy на Nginx; TLS через Let's Encrypt; весь внешний трафик по HTTPS.
- VPN для административного доступа (БД, брокер, мониторинг недоступны из публичной сети).

**Definition of Done:** доступ к серверам только по ключам; открыты только необходимые порты; весь трафик по HTTPS; админ-плоскость доступна только через VPN.

## Шаг 0.3. Контейнеризация и хранилища

Все сервисы описываются в **Docker Compose** — инфраструктура как код. Разворачивается ядро хранилищ, на котором затем строится Этап 1:

| Сервис | Образ/роль | Проверка готовности |
|---|---|---|
| `postgres` | PostgreSQL + расширение **pgvector** | подключение проверено; `CREATE EXTENSION vector` выполняется |
| `redis` | Redis | подключение проверено; pub/sub работает |
| `rabbitmq` | RabbitMQ (с management-плагином) | подключение проверено; management-UI за VPN |

Контракты:

- инфраструктура воспроизводима из репозитория одной командой на каждом окружении;
- разделение окружений — через `.env`-файлы / секрет-менеджер, не через правку compose-файлов;
- секреты (пароли БД, креды брокера, будущие ключи LLM-провайдеров, JWT-секрет) — только в переменных окружения / секрет-менеджере, никогда в git;
- расширение `pgvector` подключается уже на Этапе 0, чтобы Этап 1 мог немедленно создавать таблицы эмбеддингов (требование ТЗ: векторный слой закладывается с первого шага).

**Definition of Done:** инфраструктура воспроизводима из репозитория; все три хранилища подняты, подключения проверены; pgvector доступен.

## Шаг 0.4. CI/CD, мониторинг, бэкапы

**CI/CD:** git-репозиторий + пайплайн сборки и деплоя (GitHub Actions / GitLab CI). Push в целевую ветку → автосборка образов → автодеплой на staging. Пайплайн прогоняет линт и тесты до деплоя.

**Мониторинг и логи:**

- метрики — Prometheus + Grafana (или Netdata);
- централизованные логи — Loki;
- базовые алерты (доступность сервисов, ошибки, заполнение диска) приходят оповещением.

**Definition of Done:** видны метрики и логи; приходят оповещения.

**Бэкапы:**

- автоматические дампы PostgreSQL по расписанию;
- политика хранения определена;
- **контрольное восстановление протестировано** — включено в Definition of Done намеренно. Бэкап без протестированного восстановления — иллюзия бэкапа.

**Definition of Done:** бэкапы по расписанию; восстановление из бэкапа выполнено и проверено хотя бы один раз на staging.

## Гейт верификации этапа

- среда поднимается из репозитория на чистом хосте без ручных шагов сверх задания секретов;
- health-check всех сервисов зелёный; pgvector, Redis pub/sub и RabbitMQ проверены;
- проведено и задокументировано одно контрольное восстановление PostgreSQL из бэкапа;
- артефакты: список команд развёртывания, commit SHA, окружение, отчёт о восстановлении бэкапа.
