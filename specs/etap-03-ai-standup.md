# Этап 3 — AI Standup Pipeline

Этап 3 полностью автоматизирует сбор ежедневной отчётности: сотруднику достаточно наговорить голосовое сообщение в Telegram-бот, а система расшифрует его, поймёт контекст, передвинет карточки на доске и обновит тайм-трекер. Это материализация анти-бюрократической позиции продукта — **CRM, которую не нужно заполнять руками**.

Закрывает киллер-фичи master-спеки: **№2 AI Standup Pipeline** и значимую часть **№6 Self-Filling CRM** (авто-перенос карточек, авто-начисление времени из голоса).

Миссия: durable-конвейер «голос → транскрипция → извлечение структурированного JSON → применение к домену», который маскирует PII перед отправкой во внешние LLM, **не доверяет** содержимому LLM-вывода как авторитету и применяет действия через те же guarded-пути, что и ручные операции (Этапы 1–2).

Non-goals этапа (выносится в Этапы 4–5):

- никакого расчёта Velocity и предиктивных сроков (Этап 4) — этот этап лишь наполняет `time_logs`, из которых Velocity считается позже;
- никакого RAG/графа знаний и вычисления эмбеддингов (Этап 5);
- никакого парсинга переписок из почты/мессенджеров в сделки (расширение фичи №6, Этап 5) — здесь только голосовые дейлики в Telegram;
- движок себестоимости не дублируется: Этап 3 создаёт `time_logs` и двигает карточки, а пересчёт принадлежит Этапу 2.

## Структура репозитория (добавления)

| Путь | Владелец | Содержимое |
|---|---|---|
| `/backend/src/modules/telegram` | NestJS | Telegram webhook, привязка аккаунтов, отправка промптов и подтверждений |
| `/backend/src/modules/standup` | NestJS | state-machine submission, оркестрация пайплайна, применение действий |
| `/backend/src/modules/ai` | NestJS | единый AI-слой: вызовы LLM/Whisper, тиринг, **маскирование PII**, кэш ответов |
| `/backend/src/workers/standup` | NestJS | фоновый воркер очереди `ai_standup` (RabbitMQ) |

Принцип владения: модуль `ai` — **единственная** точка исходящих вызовов к LLM/Whisper. Все шаги конвейера проходят через него, и маскирование PII обойти нельзя. Применение действий идёт через существующие сервисы (`BoardModule`/`TasksModule` для переносов, `TimetrackingModule` для `time_logs`) — у ИИ нет привилегированного бэкдора в БД.

## Шаг 3.1. Интеграция Telegram-бота и Speech-to-Text

Бот по расписанию опрашивает сотрудников; сотрудник отвечает голосовым; голос отправляется в **OpenAI Whisper API** для транскрипции в сырой текст.

### Контракт привязки аккаунта (identity)

Telegram-аккаунт должен быть достоверно связан с пользователем CRM **до** любого применения действий:

- привязка через одноразовый код: пользователь в веб-CRM получает код, отправляет его боту; бот связывает `telegram_user_id` ↔ `user_id` (с `tenant_id`);
- **личность действующего лица определяется привязанным аккаунтом, а не содержимым голоса/LLM-вывода.** Поле `employee_id` из извлечённого JSON (см. пример ТЗ) — игнорируется как авторитет: актором всегда является привязанный пользователь;
- сообщения от непривязанных аккаунтов отклоняются с инструкцией по привязке.

### Контракт приёма и транскрипции

- интеграция через Telegram **webhook** (не long-polling) за Nginx/TLS; входящие обновления верифицируются (secret token вебхука);
- **дедуп по `update_id`/`message_id`**: одно и то же голосовое не обрабатывается дважды (защита от ретраев Telegram);
- приём голосового создаёт запись `standup_submission` в статусе `received` и ставит задачу в очередь `ai_standup`;
- аудио уходит в Whisper из воркера, не в webhook-цикле; результат — сырой транскрипт, статус `transcribed`;
- **оговорка по PII в аудио:** регулярное маскирование применимо к тексту, не к аудиопотоку; конфиденциальность аудио, отправляемого в Whisper, обеспечивается коммерческим аккаунтом провайдера и опцией нулевого хранения / DPA (master → AI-слой, решение data-residency из Этапа 0). Сырой транскрипт трактуется как чувствительные данные.

**DoD шага:** только привязанные аккаунты обрабатываются; голосовое транскрибируется в текст через Whisper из воркера; повторная доставка не задваивает обработку.

## Шаг 3.2. LLM-парсер намерений (текст → JSON)

Сырой транскрипт превращается в строго структурированный JSON-пакет лёгкой моделью (дешёвый тир).

### Контракт парсинга

- **маскирование PII перед LLM** (обязательно, через модуль `ai`): телефоны, e-mail, пароли и иные PII заменяются плейсхолдерами до отправки текста в модель;
- модель — дешёвый/быстрый тир (`claude-haiku-4-5` или сопоставимый), с **structured outputs / строгой JSON-схемой** — модель обязана вернуть валидный по схеме объект;
- результат валидируется по схеме на стороне бэкенда; невалидный вывод → статус `parse_failed`, сотруднику уходит просьба переформулировать;
- модель проставляет уверенность по действиям; низкая уверенность помечает действие для обязательного подтверждения (см. Шаг 3.3);
- кэш ИИ-ответов (Redis) применяется по нормализованному входу + tenant scope, как описано в master.

Каноничная схема извлекаемого пакета (по примеру ТЗ; `employee_id` присутствует, но **не используется как авторитет**):

```json
{
  "employee_id": 804,
  "actions": [
    { "task_id": 1420, "status_change": "DONE", "time_logged_minutes": 120 },
    { "task_id": 1421, "status_change": "IN_PROGRESS", "blocker_detected": "Дизайнер не прислал исходники макета" }
  ]
}
```

Конвейер `[Голосовое в Telegram] → [Whisper: текст] → [маскирование PII] → [LLM] → [валидный JSON] → [применение]`.

**DoD шага:** транскрипт маскируется до LLM; модель возвращает валидный по схеме JSON; невалидный вывод не доходит до применения.

## Шаг 3.3. Авто-актуализация канбана и триггеры алертов

Бэкенд принимает валидный JSON, передвигает карточки, начисляет время в юнит-экономику; при текстовом блокере вешает красный тег `BLOCKED` и уведомляет проджект-менеджера.

### Контракт применения (безопасность — критично)

LLM-вывод — это **данные, а не команда с правами**. Применение проходит проверки:

- **авторизация по привязанному пользователю.** Действия применяются от имени привязанного `user_id` с его правами (tenant + проектный доступ + RBAC). Тот же guarded-путь, что и ручные действия;
- **валидация целей.** Каждый `task_id` обязан принадлежать tenant пользователя и проекту, где у него есть доступ (как правило — назначенная ему задача). Чужие/несуществующие `task_id` отклоняются и помечаются в результате, а не применяются;
- **маппинг статусов.** `status_change` (`DONE`/`IN_PROGRESS`/…) транслируется в перенос задачи в соответствующую колонку доски через `BoardModule` (эмитит `task.moved`); закрытие (`DONE`) ставит `closed_at` и (на Этапе 5) задачу на эмбеддинг;
- **начисление времени → через тайм-трекинг Этапа 2.** `time_logged_minutes` создаёт запись `time_logs` (с `timestamp_start/end`, выведенными из now − длительность) через `TimetrackingModule`, что триггерит движок `economics`. Этап 3 **не пишет** себестоимость напрямую;
- **блокер.** `blocker_detected` ставит `tasks.is_blocked = true` и поднимает `alert` (тип `task_blocked`) с уведомлением PM через очередь `notifications`; событие `task.blocked`/`alert.raised`.

### Контракт подтверждения (human-in-the-loop, по умолчанию)

Поскольку применение затрагивает денежное состояние (начисление времени → себестоимость), по умолчанию включён шаг подтверждения:

- бот возвращает человеко-понятную сводку распознанных действий с инлайн-кнопками «Подтвердить / Изменить / Отменить»;
- применение происходит только после подтверждения; статус `awaiting_confirmation` → `applied`;
- действия с низкой уверенностью требуют подтверждения всегда;
- **настройка tenant** `standup_auto_apply` может переключить на полностью автоматический режим (ТЗ: «автоматически передвигает карточки») — тогда действия применяются сразу, но с окном отмены и полным аудитом. Подтверждение по умолчанию — ответственный дефолт; авто-режим — осознанный выбор арендатора.

> Решение по дефолту: подтверждение включено из коробки, потому что ошибка авто-начисления времени искажает финансы. Это конфигурируется на уровне tenant — продуктовый «вау» (отсутствие планёрок) сохраняется, а доверие к финансам не страдает.

**DoD шага:** валидные действия применяются от имени привязанного пользователя через guarded-пути; чужие `task_id` отклоняются; время начисляется через тайм-трекинг (не напрямую в себестоимость); блокер вешает тег и уведомляет PM; подтверждение включено по умолчанию и конфигурируется.

## State-machine конвейера и durability

Каждое голосовое — это durable-запись `standup_submission` с явной машиной состояний; конвейер восстановим после падения воркера на любом шаге.

```text
received -> transcribing -> transcribed -> parsing -> parsed
         -> awaiting_confirmation -> applied
         -> parse_failed
         -> rejected            (отмена пользователем / провал валидации целей)
         -> failed              (внешняя ошибка после ретраев)
```

Правила:

- источник истины — `standup_submissions` в PostgreSQL; сообщение `ai_standup` не является состоянием;
- каждый переход идемпотентен; повторная доставка сообщения по `dedup_key` (производному от `message_id`) не повторяет уже выполненный шаг;
- применение действий идемпотентно по `(submission_id, индекс_действия)` — повторный `applied` не задваивает `time_logs` и переносы;
- каждое применённое действие пишет ссылки на созданные сущности (`time_log_id`, факт переноса) для аудита и окна отмены.

```sql
-- Привязка Telegram-аккаунта к пользователю CRM.
CREATE TABLE telegram_accounts (
    id               BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id        BIGINT NOT NULL REFERENCES tenants(id),
    user_id          BIGINT NOT NULL REFERENCES users(id),

    linked_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (telegram_user_id),          -- один TG-аккаунт = один пользователь
    UNIQUE (tenant_id, user_id)
);

-- Одноразовые коды привязки.
CREATE TABLE telegram_link_codes (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id   BIGINT NOT NULL REFERENCES tenants(id),
    user_id     BIGINT NOT NULL REFERENCES users(id),
    code        VARCHAR(16) NOT NULL,
    expires_at  TIMESTAMPTZ NOT NULL,
    used_at     TIMESTAMPTZ NULL,
    UNIQUE (code)
);

-- Машина состояний дейлик-сабмишена.
CREATE TABLE standup_submissions (
    id                  BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id           BIGINT NOT NULL REFERENCES tenants(id),
    user_id             BIGINT NOT NULL REFERENCES users(id),
    telegram_message_id BIGINT NOT NULL,
    status              VARCHAR(32) NOT NULL,        -- см. state-machine
    audio_file_ref      VARCHAR(255) NULL,           -- ссылка на временный аудио-артефакт
    transcript_raw      TEXT NULL,                   -- чувствительные данные
    transcript_masked   TEXT NULL,                   -- то, что ушло в LLM
    parsed_json         JSONB NULL,                  -- валидированный по схеме результат
    confidence          NUMERIC(4,3) NULL,
    error_code          VARCHAR(48) NULL,
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    applied_at          TIMESTAMPTZ NULL,
    UNIQUE (telegram_message_id)                     -- дедуп доставки
);
CREATE INDEX idx_standup_status ON standup_submissions (tenant_id, status);

-- Применённые действия (аудит + окно отмены).
CREATE TABLE standup_actions (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id     BIGINT NOT NULL REFERENCES tenants(id),
    submission_id BIGINT NOT NULL REFERENCES standup_submissions(id),
    action_index  INT NOT NULL,
    task_id       BIGINT NULL REFERENCES tasks(id),
    kind          VARCHAR(32) NOT NULL,              -- status_change | time_log | blocker
    applied_time_log_id BIGINT NULL REFERENCES time_logs(id),
    result        VARCHAR(32) NOT NULL,              -- applied | rejected_foreign | rejected_invalid
    detail        JSONB NULL,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (submission_id, action_index)             -- идемпотентность применения
);

-- Расписание опроса сотрудников.
CREATE TABLE standup_schedules (
    id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id    BIGINT NOT NULL REFERENCES tenants(id),
    cron_expr    VARCHAR(64) NOT NULL,               -- когда опрашивать
    timezone     VARCHAR(48) NOT NULL,
    prompt_text  TEXT NOT NULL,
    target_role  VARCHAR(32) NULL,                   -- кого опрашивать
    is_active    BOOLEAN NOT NULL DEFAULT TRUE
);

-- Переключатель авто-применения на уровне арендатора.
ALTER TABLE tenants
    ADD COLUMN standup_auto_apply BOOLEAN NOT NULL DEFAULT FALSE;
```

Контракты схемы: `telegram_accounts.telegram_user_id` уникален глобально (один TG-аккаунт не действует за двоих); `standup_submissions.telegram_message_id` уникален (дедуп); `standup_actions (submission_id, action_index)` уникален (идемпотентность). Всё scoped по `tenant_id`.

## Контракт очереди `ai_standup`

| Поле сообщения | Назначение |
|---|---|
| `kind` | `transcribe` \| `parse` \| `apply` |
| `tenant_id` | scope |
| `submission_id` | целевой сабмишен |
| `dedup_key` | производный от `telegram_message_id` |

Правила: воркер идемпотентен; источник истины — `standup_submissions`; долгие вызовы Whisper/LLM выполняются только в воркере, не в webhook-цикле; при падении переход повторяется без повторного применения уже выполненного.

## Контракт AI-слоя (повторное использование master)

- **единая точка egress:** все вызовы Whisper/LLM — через модуль `ai`; маскирование PII встроено и неотключаемо для текста, идущего в LLM;
- **тиринг:** парсер намерений — дешёвый тир (`claude-haiku-4-5`); аналитические задачи (сводки) — аналитический тир — но они принадлежат Этапу 4/5, не этому;
- **structured outputs:** парсер использует строгую JSON-схему; невалидный результат не применяется;
- **кэш Redis:** повторяющиеся входы отдаются из кэша без платного запроса;
- **юридический контракт:** коммерческие аккаунты провайдеров, нулевое хранение/DPA, размещение трафика по data-residency Этапа 0.

## Realtime-события Этапа 3

Применение действий ИИ переиспользует доменные события Этапов 1–2 — доска и дашборды обновляются так же, как при ручных действиях:

| Событие | Финансовое? | Источник |
|---|---|---|
| `task.moved` | нет | маппинг `status_change` |
| `task.blocked` | нет | `blocker_detected` |
| `task.cost_changed` / `project.pnl_changed` | **да** | следствие созданного `time_log` → движок Этапа 2 (только internal-роли) |
| `alert.raised` | **да** для маржи / нет для блокера | по типу |
| `standup.applied` | нет | сводка применённого дейлика (участникам/PM) |

Изоляция финансов от роли `client` (фича №9) сохраняется без изменений.

Минимальные группы тестов:

| Группа | Минимальные кейсы |
|---|---|
| привязка | непривязанный аккаунт отклонён; код одноразовый и истекает; один TG-аккаунт ↔ один пользователь |
| дедуп/идемпотентность | повтор `telegram_message_id` не задваивает обработку; повторный `apply` не задваивает `time_logs`/переносы |
| маскирование PII | телефоны/e-mail/пароли заменены до отправки в LLM; обойти egress нельзя |
| валидация вывода | невалидный по схеме JSON не применяется; низкая уверенность → обязательное подтверждение |
| **безопасность применения** | `employee_id` из JSON игнорируется; чужой/несуществующий `task_id` отклонён; действия идут с правами привязанного пользователя (RBAC/tenant) |
| начисление времени | `time_logged_minutes` создаёт `time_log` и триггерит движок Этапа 2; себестоимость напрямую не пишется |
| блокер | `blocker_detected` ставит `is_blocked` и поднимает алерт с уведомлением PM |
| подтверждение/отмена | по умолчанию применение после подтверждения; undo откатывает действия; авто-режим работает по флагу tenant |
| client-изоляция | роль `client` не получает финансовых следствий дейлика ни в REST, ни в WebSocket |
| recovery | падение воркера на любом шаге восстанавливается без потери/двойного применения |

Артефакты: команды и коды выхода; вывод тестов; список миграций; commit SHA на staging. Внешние Whisper/LLM в тестах замоканы; реальные ключи в тестах не используются.

Этап 3 принимается только при проходящих тестах безопасности применения, маскирования PII и идемпотентности. Демонстрация «голос двигает карточку» без этих тестов приёмочным артефактом не является.

## Контрольная точка этапа

По завершении Этапа 3 сотрудник наговаривает дейлик в Telegram — система маскирует PII, извлекает структурированные действия, показывает сводку на подтверждение и применяет их через те же guarded-пути, что и ручная работа: карточки двигаются, время начисляется в юнит-экономику Этапа 2, блокеры подсвечиваются и уведомляют PM. Накопленные `time_logs` становятся данными для расчёта Velocity на Этапе 4, а закрытые задачи — кандидатами на эмбеддинги для графа знаний Этапа 5.
